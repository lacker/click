# Glossary

This glossary defines Click and theorem-proving terms for programmers. Each
definition is intentionally short; follow its links for the operational model.

## How nearby terms differ

Several words describe the same proposition at different stages. A
**proposition** is the neutral logical statement. A **claim** is a proposition
or contract property selected for verification. A **goal** is an open judgment
in the proof state. An **obligation** is a condition generated by semantic
evaluation that still needs justification. Once established, a proposition is
a **fact**; it is an **assumption** when the current context accepts it as an
input and a **premise** when a particular rule consumes it.

The proof artifacts are also distinct. A **proof clause** contains source
syntax, usually a **proof script**. Checking advances the **proof state**
through checked operations; internally, a persistent **proof object** retains
that state and its transition history. Expansion can serialize part of that
history as an explicit proof, sometimes called a **certificate**. **Kernel
derivations** are the trusted evidence underlying checked transitions.

For execution, a **program point** is a location in the C function. An
**execution frontier** combines one current program point with its symbolic
state and pending continuations. A branch's **arms** may create several
path-local frontiers, one for each feasible **execution path**; continuing arms
join at a shared **continuation**. A **snapshot** records state for later
reference; an **outcome** is a completed path with its final state, while a
**result** is only the value returned by that path.

## A

### Abstract resource

A named logical resource whose meaning is supplied by its contracts rather
than by a body that Click can unfold. Abstract resources transfer by exact
resource rules. Contrast with [composite resource](#composite-resource).

### Alias

A pointer or reference that can designate storage also designated by another
  value. Click tracks the permissions needed to reason soundly in the presence
  of aliases. See [Aliasing and frames](../concepts/aliasing-and-frames.md).

### Ambient fact

A fact available in the current proof context but not named as an explicit
premise of the current tactic. Smart tactics may search ambient facts; a simple
tactic uses only the facts its surface form selects.

### Antecedent

The proposition before `implies` in an implication. An implication can be used
only after its antecedent is established; its proposition after `implies` is
the consequent.

### Arm

One syntactic alternative of a proof or C branch, such as the `then` arm and
the `else` arm. An arm can produce zero or more feasible execution paths.

### Assumption

A proposition temporarily available as true in a proof context. A contract
  requirement becomes an assumption when Click verifies the function body.

### Audit

A whole-workflow check that discovers smart proof sites, expands them, verifies
  the rewritten source, and applies performance policy. See [Audit](../concepts/audit.md).

### Authority

Checked evidence that permits a proof or state transition. A kernel derivation
is proof authority; a viewed or owned resource can grant memory-access
authority; `allocation(base, bytes)` grants lifetime authority for one heap
allocation.

### Availability

Whether a fact or resource can be selected in the current proof context. Exact
availability is indexed membership after canonicalization. A fact needed at a
different state requires a checked transport or another documented rule that
records the necessary evidence.

### Axiom

A trusted, theorem-producing kernel operation. Click uses *axiom* for both a
single primitive rule and a parameterized family of such rules; it does not
mean an unproved Surface Click theorem declaration. See [Proof
landscape](../concepts/proof-landscape.md).

## B

### Binder

A syntax form that introduces a local name, as in `forall (x: int32)` or
  `|acc, k|`. The name is in scope only in the associated body.

### Bitvector

A fixed-width sequence of bits interpreted by operations such as shifts and
bitwise conjunction. Click represents C integer values with bitvector terms
while checking signed overflow and other C definedness conditions separately.

### Borrow

Scoped permission to use authority without taking ownership. A callee's `views`
requirement can borrow from the caller's owned resource for the duration of the
call without consuming it or creating a new persistent view afterward.

### Bounded search

Search stopped by deterministic work budgets. Failure to find a proof within
  the budget doesn't mean that the claim is false. See [Smart and simple
  tactics](../concepts/smart-and-simple-tactics.md).

### Branch

One path created by a conditional or by proof case analysis. Branches carry
  path-specific facts and must satisfy the required join conditions.

## C

### C fragment

C syntax embedded in a Click contract or tactic to identify an expression,
  statement, or program point. A fragment is resolved against the verified C
  function; it isn't executed as a separate program.

### C0

Click's deliberately supported subset of C. It is the verification boundary,
  not a claim to implement every ISO C behavior. See [Supported C0](language/c0.md).

### Canonical form

The deterministic representation Click uses for definitional comparison. A
term is in canonical form when each memory load has been resolved or replaced
with its load variable; arithmetic order and proved equalities are unchanged.
See [Canonicalization](../internals/canonicalization.md).

### Canonicalization

Conversion of a term to its canonical form. Canonicalization removes only
representation differences that need no proof; it never consumes an ambient
equality fact.

### Cell epoch

The most recent memory-derivation point that might have written one cell. Loads
from snapshots connected without a possible write share the same cell epoch and
therefore the same load variable.

### Certificate

A surface-expressible explicit proof used as independently checkable output,
most notably by expansion. Internally, `ProofCertificate` is a structured
serialization of simple operations; it carries no semantic authority and need
not be materialized during ordinary verification.

### Certificate step

One surface-expressible simple operation in the internal certificate
serialization. `SimpleProofStep` is the main implementation type. The
corresponding checked transition, not the serialized step by itself, advances
the proof state.

### Certification

Independent checked construction of the kernel authority needed to accept a
claim, contract, or transition. Planning can propose evidence, but certification
reconstructs or validates it without trusting the planner's success result.

### Claim

One property selected for verification and reporting. For a C function, a
claim is normally one `ensures` or effect clause; a grouped proof packages all
of the function's claims under one contract label. A claim may create several
goals and obligations.

### Completeness

The ability of a proof procedure to find every true result in a stated
  domain. Click's bounded smart tactics are intentionally incomplete;
  incompleteness doesn't weaken soundness.

### Composite resource

A named logical resource with a body of facts and contained resources that
Click can expose with `unfold` and rebuild with `fold`. Contrast with
[abstract resource](#abstract-resource).

### Condition fact

A pure fact of the form `ConditionIs(condition, polarity)` in Kernel Click.
It records that a lowered Boolean condition is true or false; branch conditions
and many C comparisons use this representation.

### Conjunction

A proposition of the form `P and Q`, true only when both component propositions
are true. The components are called conjuncts.

### Consequent

The proposition after `implies` in an implication. Establishing the antecedent
allows the consequent to be derived.

### Consumption

Removal of a resource fact from the current resource context when an operation
uses or transfers it without returning it. Pure proposition facts aren't
consumed by use.

### Continuation

The C or proof work that resumes after a nested branch or loop region. A joined
branch has one shared continuation, which must not depend on facts available in
only one arm.

### Contract

A modular specification of a C function, including requirements, guarantees,
  effects, resources, and structural obligations. See
  [Contracts](../concepts/contracts.md).

### Contradiction

Evidence that the current assumptions cannot all hold, such as exact facts `P`
and `not P`. From a contradiction, any proposition follows; the
`contradiction` tactic records the conflicting evidence explicitly.

### Control-flow tactic

A tactic that follows or structures C execution, such as `if`, `branch`, or
  `loop`. See [Tactics](tactics/index.md).

## D

### Definedness

The condition that evaluating a C or Click expression stays within Click's
  modeled rules, including arithmetic and memory rules. `defined(e)` states
  this condition explicitly.

### Definitional equality

Equality that follows from Click's representation rules and therefore needs
no proof fact. Equality of canonical forms is definitional. Arithmetic
identities, assignments, and frame-dependent equalities are instead proved
equalities and require evidence.

### Derivation

Structured evidence that a conclusion follows from specific premises by a
named kernel rule. A derivation is proof authority; a search result or cached
Boolean answer is not.

### Disjunction

A proposition of the form `P or Q`, true when at least one component proposition
is true. The components are called disjuncts; case analysis proves a goal under
each feasible disjunct.

## E

### Effect

A contract clause that describes what a function may change in memory or in
an abstract resource. Body verification proves the implementation stays inside
that effect; callers use the checked effect as the change boundary.

### Elaboration

Context-dependent translation from convenient Surface Click forms into more
  explicit checked forms before kernel lowering.

### Entailment

A checked relationship in which one fact or resource state is sufficient to
establish another. For example, owned memory entails its viewed core, and a
larger range can entail access to a covered subrange.

### Execution fact

A pure fact produced or certified while symbolically executing one path. The
`ExecutionPureFact` representation can also record whether the fact is public,
which store produced it, or how it was transported. Some implementation fields
historically call these *effect facts*; use *execution fact* in prose.

### Execution frontier

The boundary between C already executed and C still pending on one path. It
contains one current program point, the symbolic state there, and the
continuation stack. A proof with several open paths can contain several
path-local frontiers.

### Execution path

One symbolic route through C control flow, paired with its path conditions
  and symbolic state.

### Execution proof

A proof that advances an execution frontier and establishes a relationship
between the entry and exit of a C region. Contrast with a [pure
proof](#pure-proof), which reasons at one program point.

### Expansion

Replacement of smart proof syntax with an explicit proof extracted from its
checked transition history. Click verifies the complete rewritten source. See
[Expansion](../concepts/expansion.md).

## F

### Fact

A proposition established and available in the current proof state. Facts
  can come from requirements, execution, theorem application, or earlier proof
  steps.

### Fact transport

A checked transition that relates an exact source fact at one snapshot to a
target fact at another. Direct statement transport uses a bounded frame check;
the `transport` tactic can select additional explicit evidence.

### Focus

The open goal selected for the next proof operation. Focusing changes which
goal a tactic addresses; it does not make an unproved proposition available as
a fact.

### Fold

To replace an exposed composite-resource body with its named form. Folding
consumes the required body facts and resources and produces the composite
resource fact. Predicates can be unfolded but don't have a corresponding
surface `fold` operation.

### Footprint

The memory ranges and logical resources an operation owns, reads, writes, or
may change. A contract effect describes an allowed change footprint, while a
resource body can expose an ownership footprint.

### Frame

The state outside an operation's effect, or the reasoning that proves this
state is unchanged. Frame reasoning can preserve facts across execution and
can prove that actual writes stay inside a declared effect.

### Frame condition

An obligation relating an operation's pre-state, post-state, and declared
effect. It proves preservation outside the allowed footprint or coverage of
the actual changes. The `frame` tactic proves these conditions.

### Frontier

Short for [execution frontier](#execution-frontier) when discussing a proof.
In reports, *diagnostic frontier* instead means the boundary of completed work
in a partial run.

## G

### Ghost state

Proof-only state that doesn't exist in the executable C program. Click calls
this *spec state* and currently represents it through immutable spec terms,
proof-local witnesses, snapshots, and logical resources rather than arbitrary
mutable ghost variables. See [Spec state](../concepts/spec-state.md).

### Goal

A proposition or state transition that remains to be proved. A proof is
  complete when it closes every generated goal.

## H

### Havoc

A symbolic memory transition that forgets values an operation may have changed
while retaining the frame outside its write footprint. Call havoc and loop
havoc introduce unknown post-state values; they don't mean that the verifier
chooses one random concrete mutation.

## I

### Implication

A proposition of the form `P implies Q`. It states that the consequent `Q`
holds whenever the antecedent `P` holds; it doesn't assert `P` by itself.

### Induction

Proof by a base case and a step that assumes the proposition for a smaller
  case. Click exposes induction where documented by the `induct` tactic.

### Inductive resource

A recursive composite resource whose guarded body contains a structurally
smaller instance of the same resource. Click can use the declared child as a
termination measure for supported recursive traversals.

### Instantiation

Substitution of a concrete term for a quantified binder. The `instantiate`
  tactic derives a particular consequence from a universal fact.

### Invariant

A proposition or resource condition that holds initially and is preserved by
  every loop iteration. It summarizes arbitrarily many iterations.

## J

### Join

The point where multiple symbolic paths are reconciled into a state suitable
  for following common control flow.

## K

### Kernel

The small trusted checker and semantic core that validates primitive proof
  steps. See [Kernel](../internals/kernel.md).

### Kernel Click

Click's internal, explicit representation after validation and lowering.
  Kernel Click has no user-facing textual syntax.

### Kernel derivation

A typed theorem, proof tree, or transition evidence produced by a trusted
kernel rule and naming the exact premises it used. Checked proof operations
construct or validate these derivations; they don't trust the planner that
selected an operation.

### Kernel variable

A term standing for a value the kernel doesn't know concretely: a function
parameter at entry, a local a loop may modify, the result of an opaque call,
or the contents of an unknown memory cell. Kernel variables are anonymous
ids, not C names; they appear in facts and goals and are related to each
other only through facts. A load variable is one kind of kernel variable.

## L

### Linear resource

A resource whose owned authority cannot be copied freely. Click tracks owned
memory linearly across calls: a transfer must return, consume, or replace the
resource according to the callee's contract.

### Load term

A Kernel Click term `load(memory, pointer)` denoting the value read from one
memory snapshot. Canonicalization resolves a known cell immediately or replaces
the remaining load term with its load variable.

### Load variable

A kernel variable that serves as the canonical form of an unresolved memory
load. The loaded cell and its derivation epoch identify the variable, so reads
connected by steps proved not to write that cell use the same variable. A
defining fact equates it to the load it represents. Load variables differ
from other kernel variables only by a reserved id range, not by type.

### Loadability

Evidence that a memory access can read the required bytes at a pointer in a
  particular memory state. See [Loadability](../concepts/loadability.md).

### Lowering

Translation from validated Surface Click into kernel propositions, terms,
  contracts, and proof operations.

## M

### Materialization

Making an implicit value or fact explicit for one consumer. Memory
materialization resolves a load from a snapshot's recorded cell; resource
materialization derives one requested proposition from compact resource
authority. It is not another name for fact transport.

### mdtest

A repository fixture consisting of C, Click, and expected-result sections in
Markdown. The gate verifies mdtests with deterministic bounds.

### Memory block

The allocation identity at the base of a kernel pointer. Two pointers in
different blocks cannot alias; offsets locate ranges and cells within one
block. Stack objects, heap allocations, and symbolic external storage receive
distinct block identities.

### Memory cell

A storage location selected by a pointer together with the byte width and
value type of an access. A cell belongs to one memory block and can be tracked
across snapshots that do not write it.

### Memory derivation DAG

The per-verification directed acyclic graph connecting interned memory
snapshots to the operations that produced them, such as stores, declarations,
and call havoc. It supports bounded reasoning about whether a cell changed.
See [Memory derivation DAG](../internals/memory-dag.md).

### Memory range

A contiguous half-open region of a memory block. Surface ranges use element
indices such as `p[start..end]`; lowering converts them to byte offsets in a
kernel `CMemoryRange`.

### Memory snapshot

An immutable, interned `CMemory` value representing memory at one point in
symbolic execution. A program-point snapshot contains a complete symbolic C
state; its memory component is a memory snapshot.

### Modus ponens

The rule that derives `Q` from exact facts `P` and `P implies Q`. Click uses
this rule in explicit extraction and selected simplification paths.

## N

### Negation

A proposition of the form `not P`, true when `P` is false. A fact and its exact
negation form a contradiction.

### Normalization

Deterministic reduction to a simpler equivalent form using context-free rules.
The `normalize` tactic closes a goal only when this computation produces true;
it doesn't search ambient premises or invoke general proof search.

## O

### Obligation

A proposition generated by symbolic execution or a proof rule that still
requires justification. Some execution obligations may become path assumptions
when the rule permits it; a verification condition is explicitly
non-assumable.

### `old`

A snapshot form that evaluates its subject in function-entry state rather
  than current state.

### Opaque

Hidden behind a checked interface. An opaque function call uses the callee's
verified contract without re-executing its body at the call site; an opaque
predicate or resource keeps its body unavailable until an explicit rule
exposes it.

### Outcome

One completed symbolic execution path together with its final state and, for a
returning path, its result value. A function can have several feasible
outcomes. The result is only the returned value, not the whole outcome.

### Ownership

The right represented by a resource or permission to rely on, transform, or
transfer some state. Click models ownership explicitly rather than inferring
exclusive access from a C pointer alone.

## P

### Partial correctness

The guarantee that every terminating execution satisfies its specification,
without claiming that execution terminates. A loop or function needs separate
termination evidence to establish total correctness.

### Path condition

A condition known to hold on one symbolic execution path, normally introduced
by choosing a branch arm. The opposite arm receives the opposite polarity.

### Permission

Evidence authorizing a particular view or operation on state. Permissions
  support modular reasoning about reads, writes, aliases, and frames.

### Point proof

An internal proof operation at a fixed program point. It can refine
propositions or logical resources but does not advance C execution. Pure proofs
and result-aware outcome proofs are point-proof contexts with different
available data.

### Population

The exact number of equal owned units of one declared resource. The
`count(resource(arguments))` form observes this quantity, and resource
contracts can transfer units one at a time.

### Postcondition

A guarantee that must hold at a successful function outcome, normally written
  with `ensures`.

### Precondition

A fact or resource the caller must supply, normally written with `requires`.

### Predicate

A named, parameterized proposition definition. Predicate facts can remain
opaque for modular reasoning or expose one body layer through `unfold`.

### Premise

A proposition required before a theorem or reasoning rule can establish its
  conclusion.

### Profiling

Attribution of verifier work and elapsed time to proof sites. See
  [Profiling](../concepts/profiling.md).

### Program point

A selectable location in C execution, such as function entry, statement entry
or exit, and function exit. `at(...)`, `mark`, and `execute_until` refer to
program points; an execution frontier also carries state and continuations.

### Proof

Evidence that every goal generated by a claim is valid under its assumptions.

### Proof clause

The `by ...` source attached to a theorem, contract claim, effect, or loop
phase. A clause can request a default smart tactic, one tactic, or an explicit
proof script.

### Proof context

The facts, resources, local bindings, selected snapshots, and structural data
available to a proof operation. An *assumption context* or *fact context* is a
narrower internal index over the proposition facts in that context.

### Proof mark

A named point in proof execution, created by `mark`, that later tactics can
  select or compare.

### Proof object

The internal persistent representation that owns open goals, semantic state,
and checked successor transitions during proof construction. Cheap structural
sharing lets smart tactics search alternatives efficiently. Proof authors
interact with the [proof state](#proof-state), not with this implementation
object. Kernel evidence types are called [kernel derivations](#kernel-derivation)
in prose.

### Proof script

An ordered Surface Click tactic block inside a proof clause. A script can mix
simple, smart, and control-flow tactics. An expanded script containing only
surface-expressible checked operations can serve as a certificate.

### Proof site

A source location containing a selectable proof or tactic occurrence.
Profiling attributes work to proof sites, and expansion rewrites a selected
smart site only after the complete rewritten source verifies.

### Proof state

The current goals, facts, symbolic execution frontier, resources, and
  bookkeeping needed to continue a proof.

### Proof unit

A selectable claim-sized unit verified and reported independently, such as a
  contract clause or theorem claim.

### Proposition

A statement that can be true or false and can therefore be assumed or proved.

### Proved equality

An equality established by a fact or kernel derivation rather than by
canonical representation alone. A tactic that uses proved equality must name
or retain checked evidence for it. Contrast with [definitional
equality](#definitional-equality).

### Pure fact

A fact represented by a Kernel Click proposition rather than by a logical
resource. Condition facts, equalities, bounds, and quantified propositions are
pure facts.

### Pure proof

A proof that derives a proposition at one program point without advancing C or
transforming logical resources. Theorem proofs and the nested body of `have`
are pure proofs.

## Q

### Quantifier

`forall` or `exists`, which states a proposition for every value or for at
  least one value of a type.

## R

### Replay

Checking a previously produced explicit proof again. Current implementation
names use *replay* for compatibility paths that interpret certificates through
a parallel state representation. Replay isn't a required phase of the proof
model: explicit and smart tactics can advance the same checked proof object
directly, while expansion verifies its rewritten Surface Click through the
ordinary entry point.

### Resource

A logical representation of owned state with rules for transfer, splitting,
  combination, and consumption.

### Resource context

The proof-side state containing the resource facts currently held on one path.
It is separate from the pure fact context and changes when resources are
transferred, consumed, produced, folded, or unfolded.

### Resource fact

A held instance of a logical resource in the proof state. Unlike a pure fact,
a resource fact can be consumed, split, combined, unfolded, folded, or
transferred according to its resource definition.

### Resource family

A group of related resources governed by one algebra for validity, entailment,
composition, splitting, core views, and consumption. Memory resources are the
main built-in family; declared resources use exact-match family rules.

### Result

The value returned by one successful C execution outcome and referenced as
`result` in a postcondition. An outcome also contains final state and path
facts; a result does not.

## S

### Satisfiable

Describes a set of propositions for which at least one modeled state or value
assignment makes every proposition true. *Unsatisfiable* means no such state or
assignment exists and therefore the propositions are contradictory.

### Selector

Surface syntax that identifies a fact, requirement, resource, goal, proof
site, or program point for an operation. Checking resolves a selector against
the current state and rejects it when the selected item is absent or ambiguous.

### Separation

A proved non-overlap or independence relationship between resources or memory
ranges. Separation can justify alias checks, framing, and combining owned
resources without exposing their concrete addresses.

### Separation logic

A logic that treats resource composition and disjointness as part of the proof
state. Click uses separation-logic ideas for viewed and owned memory, resource
transfer, framing, and composite resources.

### Sidecar

A `.click` file associated with existing C source. It adds specifications and
  proofs without rewriting the C. See [Files and sidecars](../concepts/sidecars.md).

### Simple tactic

A bounded, explicit operation whose requested proof-state transition is
checked directly and retained in the proof object's provenance.

### Smart tactic

A heuristic planner that searches by trying checked simple or structural
operations on persistent proof states. Search is untrusted and can succeed
only with a completed checked state.

### Snapshot

An immutable reference to state at a selected program point, used by `old`,
`at`, marks, and memory comparisons. A program-point snapshot records a
complete symbolic C state; a load term embeds only its memory snapshot.

### Sort

The logical type of a Kernel Click term or variable, such as a 32-bit bitvector,
pointer, memory value, C state, or function outcome. Sort checking prevents
rules from combining terms from incompatible logical domains.

### Soundness

The property that Click accepts only claims justified by its modeled
  semantics and trusted rules. Soundness is distinct from search completeness.

### Source occurrence

One exact tactic occurrence in the parsed source, identified independently of
other textually identical tactics. Profiling and expansion retain this identity
through nested paths and source rewrites.

### Substitution

Replacement of a variable or matching term by another term, with binders and
types respected. Instantiation substitutes for a quantified binder; rewriting
substitutes using a proved equality.

### Surface Click

The user-facing language parsed from `.click` files.

### Surface form

A Surface Click proposition, term, selector, or tactic that represents a
checked kernel meaning in source syntax. Prefer *surface form* for the
representation and *spelling* only for literal token choices.

### Surface synthesis

Producing a Surface Click form for a kernel proposition or term so an expanded
proof can cite it. It is a checked partial reverse of lowering: the synthesized
form must lower back to the same kernel meaning at the point where the expanded
proof uses it.

### Symbolic execution

Evaluation of C over symbolic values and path conditions so one proof can
  cover many concrete inputs.

### Symbolic memory

An immutable memory state whose cells can contain concrete values, symbolic
values, or unresolved loads. Symbolic execution produces new memory snapshots
connected by the memory derivation DAG.

### Symbolic state

The modeled C state on one execution path: local values, parameters, memory,
and any path-specific execution data. `CState` is the kernel representation;
logical proof facts and resources live alongside it rather than inside it.

### Symbolic value

A term representing an input, load, call result, or computation whose concrete
runtime value isn't fixed. Facts constrain which concrete values it can denote.

## T

### Tactic

A proof-script command that requests a transition of the current proof state.

### Term

A Kernel Click expression denoting a symbolic value: a constant, a
  variable, arithmetic over other terms, or a memory load from a snapshot.
  Symbolic execution, lowering, and contract evaluation each produce terms,
  and different terms can denote one value.

### Termination

The property that execution cannot continue forever. Click records termination
separately from partial correctness and requires a checked decreasing measure
for supported loops and recursive calls.

### Theorem

A named proposition with a checked proof that can be applied in later proofs.

### Theory prover

A checked decision or derivation procedure for one logical domain, such as
bitvector arithmetic, orders, equality, or memory separation. It is distinct
from the smart planner: a theory result is accepted only through kernel rules
and checked evidence.

### Trusted computing base

The implementation whose correctness is assumed when treating a successful
Click verification as valid. Smart search is outside this boundary because it
can advance proof state only through checked operations.

## U

### Undefined behavior

A C operation for which the modeled language assigns no valid program
  behavior. Click requires proofs to rule it out on verified paths.

### Unfold

To replace one named predicate or composite resource with one layer of its
body. Unfolding a resource consumes the composite fact and exposes its immediate
body facts and resources; it doesn't recursively expose every nested layer.

## V

### Validity

Truth under all modeled executions or interpretations allowed by the
assumptions. For resource states, *validity* more specifically means that the
composed resources are coherent, such as having no overlapping exclusive
ownership.

### Verification condition

A non-assumable proof obligation generated by C semantics or a trusted rule,
such as an overflow, memory-safety, or contract condition. Click must prove it
from available evidence; it cannot continue by treating the condition as a
path assumption.

### View

A logical interpretation of underlying state, usually represented through a
  resource or permission and related to other views by explicit rules.

## W

### Witness

A concrete term supplied to prove an existential proposition. The `witness`
  tactic chooses it.

## Special forms

### `at`

A proposition or expression form interpreted at a selected snapshot or proof
  point rather than at the current state.
