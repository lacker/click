# Supported C0

C0 is this repository's small C subset. It is not a standard language. The
subset exists so proof features can be developed against a precise target before
Click grows toward real C. When C0 syntax appears inside Surface Click, this
documentation calls that syntax a **C fragment**.

## C implementation target

The initial concrete target is `x86_64-linux-kernel`: the existing LP64 data
layout with eight-bit, unsigned plain `char`. This follows the Linux kernel's
explicit `-funsigned-char` build setting, not the default of every x86-64 C
compiler. The settings are centralized in `CTarget`; LP64 alone does not imply
char signedness. `char` remains a distinct C type from `unsigned char`.

Header discovery and expansion use the profile's modeled predefines, including
`__CHAR_UNSIGNED__`, `__CHAR_BIT__`, LP64 type-size macros, Linux/x86-64 markers,
`__KERNEL__`, and byte-order constants. These are not a complete compiler macro
environment: compiler-version and feature-test macros are not synthesized.

Verification results apply to this supported subset under these assumptions,
not to every C target or every Linux kernel compiler option. The verifier does
not discover the user's compiler flags or prove portability to signed-char,
32-bit, or differently laid-out builds. Target selection, compiler-provided
layout validation, and symbolic target-independent proofs remain future work.

The `click verify` command prints the target, verified C theorem results expose
it through `target()`, and incremental verification markers include its name.

## Program-entry static ownership

A definition of parameterless `main` in the selected C sources is verified
as program startup. Its entry state owns each defined writable static object
once, at its C-initialized value, and has read-only views of const objects.
This includes file-scope objects, function-local statics, and storage in
data-only translation units. Repeated external declarations share storage;
private objects retain translation-unit or function-qualified identities.

The permissions use the existing typed memory ranges, with byte ranges for
padding and opaque union storage. This does not introduce cross-width
ownership conversion or a module concept. With no explicit effect clause,
the startup frame permits writes to its writable static storage; explicit
effect clauses may restrict that frame.

Startup proofs currently require no parameters or preconditions. They are
not reusable function contracts: an ordinary call to `main` cannot assume
startup values or receive fresh permissions. This slice does not model
`argc`/`argv`, constructors before main, or separate library-initialization
proofs. Owned global ranges can be folded into named resources and transferred
through helper contracts. Resource tactics retain the current function's
static bindings, including parameter shadowing; unfolding scalar ranges keeps
their declared signedness and width. Private-wrapper example coverage remains
tracked in
[private static ownership](https://github.com/lacker/click/blob/master/issues/private-static-helper-ownership.md).

See `mdtests/program_entry_static_ownership.md` for ownership transferred
through two calls to a pointer-taking helper without resetting the state.

## Supported types

- `int32`
- `uint8`
- `char`, an unsigned eight-bit C type distinct from `unsigned char` on the
  supported kernel target, with scalar, pointer, pointer-cell, and array forms
- `int16`/`short` and `uint16`/`unsigned short`
- `uint32`
- `int64`/`long`/`long long` and `uint64`/`unsigned long`/`unsigned long long`
- C `_Bool` and the modeled `stdbool.h` spelling `bool`; both use one-byte
  storage and normalize values to `0` or `1`
- `float` (IEEE-754 binary32) and `double` (IEEE-754 binary64) as typed value
  types with width-preserving arithmetic, comparisons, and conversions
- Standard spellings for the modeled integer types: under the supported LP64
  ABI, `int` and `int32_t` map to `int32`; `short`, `signed short`, and
  `int16_t` map to `int16`; `unsigned char` and `uint8_t` map to the one-byte
  `uint8`; `unsigned short` and `uint16_t` map to `uint16`; `unsigned int` and
  `uint32_t` map to `uint32`; `long`, `long long`, and `int64_t` map to
  `int64`; `ssize_t` also maps to `int64`; `unsigned long`, `unsigned long
  long`, `uint64_t`, and `size_t` map to `uint64`.
- The modeled `<stdbool.h>` header is a no-op include; its `bool`, `true`, and
  `false` spellings are understood directly by C0. The `true` and `false`
  constants are fallbacks when no ordinary C declaration binds that name;
  explicit macros expand before parsing.
- `void` as a function return type
- `void*` and `const void*` as opaque object pointers. They preserve pointer
  identity, provenance, nullness, and qualification, but have no modeled
  pointee width.
- Data pointers for all modeled scalar widths, including `int16*`, `uint16*`,
  `int32*`, `uint8*`, `uint32*`, `int64*`, `uint64*`, `float*`, and `double*`.
- Pointer-to-pointer forms for all modeled scalar widths, such as `int32**`
  and `uint64**`, including `float**` and `double**`.
- Pointer-to-pointer forms for named struct pointers, such as `struct node**`.
  The C0 surface retains the struct tag alongside the existing eight-byte
  pointer-cell ABI, so assignments through the cell reject pointers to a
  different struct type. File-scope struct pointers and pointer-valued
  function returns retain the same tag metadata.
- Function parameters written as a modeled scalar array, such as `int16 p[]`,
  `uint32 p[3]`, `uint64 p[]`, or `double p[]`, plus pointer arrays such as
  `int64* p[]`, lowered like C array parameters to pointers.
- Local fixed-size scalar arrays of every modeled width, including
  `int32 a[3];`, `int32 matrix[3][4];`, `uint64 values[2];`, and
  `double samples[2];`.
- Fixed-dimensional local arrays of copyable structs with nested positional
  element initializers and integer array-element designators at each dimension;
  omitted fields and elements are zero-filled.
- One-dimensional function parameters declared as arrays of supported structs;
  these decay to pointers while retaining the ABI-sized struct stride.
- Modeled function-pointer fields, such as `int32 (*compare)(int32, int32)`,
  in both pointer-backed and by-value structs. C0 retains the callback
  signature and LP64 pointer slot in field metadata; a compatible concrete
  `&function` may be stored, loaded into a local callback, dispatched, or
  called directly as `p->callback(args)`. A named Click contract can authorize
  an abstract value loaded from a struct field. [Struct subset](#struct-subset)
  covers by-value copies and `static const` callback tables.
- Copyable struct values whose fields are `int16`, `int32`, `uint8`, `uint16`,
  `uint32`, `int64`, `uint64`, `float`, `double`,
  named enum fields, modeled data pointers, modeled function pointers,
  fixed-dimensional scalar
  arrays, recursively embedded copyable structs, fixed-dimensional arrays
  of such embedded structs, or a named read-only union field; parameters,
  locals, assignments, and returns use
  independent address-backed copies.
- Named unions whose members are `int32`, `uint8`, or modeled pointer fields;
  they are embedded in structs and accessed through read-only member loads.

Pointers are semantic objects with provenance blocks and pointer-offset terms.
They are not modeled as `int32` values. The current target layout assumes
8-byte pointer objects.

An opaque object pointer such as `void *key` or `const void *key` preserves the
same provenance-carrying pointer identity as a typed object pointer while it
crosses a generic boundary. Object-pointer assignment, parameter passing,
return, equality, null checks, and explicit casts between `void *` and a
modeled object-pointer type are supported; casts preserve the pointer's
qualification metadata. An opaque pointer cannot be dereferenced, indexed,
or used in pointer arithmetic, and it does not create an ownership or memory
view. Convert it to a modeled typed pointer before accessing an object.
Function pointers are not object pointers, so a `void *` position does not
change a callback's signature. `void **` and opaque-pointer fields remain
outside this slice.

C0 accepts top-level aliases for the modeled scalar and named struct-pointer
types, such as `typedef int32_t index_t;` and `typedef struct item item_t;`.
The latter may be used as `item_t*`; copyable struct values are supported under
  the same field restrictions described below. The accepted standard
  spellings are aliases into the existing C0 type model, except that plain
`char` retains its distinct C type identity. Signed `char` and signed-char
target profiles are not yet modeled.

Direct and callback function returns may be pointers to const-qualified data, including
`const char *`. Qualification is retained across definitions, prototypes,
sidecars, external contracts, and calls. Implicit const removal is rejected.
Callback signatures retain pointee const on both returns and parameters;
incompatible qualified signatures cannot be assigned or used interchangeably.
Ordinary function declarations and definitions likewise require matching
pointee qualification on pointer parameters.
Const results permit reads when the contract supplies the necessary memory
access, but cannot be written through or implicitly converted to writable views.
Top-level const return qualifiers remain unsupported.

Pointer casts to a const-qualified pointee destination, including
`(const char *)p`, preserve the pointer's identity and add a read-only view.
Casts to supported unqualified pointer types retain the source pointer's
qualification metadata; an explicit cast does not remove const qualification.
Top-level const pointer casts remain unsupported because C0 does not represent
qualifiers on a pointer rvalue itself. The one volatile exception is a
pointer-cell view such as `(int32 * volatile *)p`: the immediate pointee cell
is marked volatile for sequential loads and stores, while the `int32` storage
reached through that cell is not. Explicit unqualified `char *` to `unsigned
char *` casts and the reverse remain supported. Other casts between modeled
typed object pointers are unsupported; identity casts preserve the source
pointer type.

Named enums are supported as four-byte `int32`-shaped scalar fields. C0
preserves the enum name and enumerator values in imported metadata, and named
enumerators such as `PACKET_READY` lower to their declared integer values in C
expressions and by-value copies. Enum parameters, return types, local
declarations, enum arrays, and anonymous enum declarations remain outside this
slice.

## Floating-point boundary

C0 models `float` as an IEEE-754 binary32 payload and `double` as an IEEE-754
binary64 payload. Slices 1 through 5 support their declared widths and LP64
alignment, parameters, locals, struct fields, arrays, allocation, typed
loads/stores, value-preserving copies, unary negation, exceptional constants,
classification predicates, C/IEEE comparisons, constant scalar conversions,
and same-width `+`, `-`, `*`, and `/`.

Decimal floating literals are converted to the declared binary format and
stored without being lowered to integers or mathematical reals. Conversion
uses round-to-nearest, ties-to-even in integer space, independent of the host
floating-point mode. The source-level constants `INFINITY` and `NAN` denote
canonical binary64 values; `INFINITYF` and `NANF` provide the corresponding
binary32 values. These constant conveniences do not override declared C
identifiers: a parameter, local, global, enumerator, or function with one of
these names keeps its declared meaning. Explicit macros expand before parsing,
and ordinary identifiers surviving compiler preprocessing retain their bindings.

The builtins `isfinite`, `isinf`, `iszero`, `issubnormal`, and
`isnan` classify a float or double expression and return `int32`; constant
arguments fold immediately and symbolic arguments become checked path
conditions. Hexadecimal
floating literals and unsupported suffixes are rejected with a source-positioned
diagnostic. `long double` remains outside the model rather than being silently
treated as the supported `double` type. The source expander likewise rejects
floating-point environment directives such as `#pragma STDC FENV_ACCESS ON`.

The value model is explicit and target-bound. `float` is IEEE-754 binary32
with four-byte size and alignment, and `double` is IEEE-754
binary64 with eight-byte size and alignment under C0's LP64 ABI. Arithmetic
operations use round-to-nearest, ties-to-even at the declared result type.
Constant arithmetic is folded in integer space; symbolic arithmetic remains a
typed, checked operation term until its operands are known. Alternate
rounding modes, `fenv` access, traps, excess precision, decimal floating point,
and compiler-specific extended precision are unsupported.

The model distinguishes finite values, signed zero, infinities, and NaNs;
copies will preserve the value representation, while generated NaNs will use a
documented canonical representation. As in C/IEEE arithmetic, `+0 == -0`, an
ordered comparison with a NaN is false, and `!=` with a NaN is true. IEEE
overflow and floating division by zero produce their specified infinity or NaN
results rather than integer-style undefined behavior. A floating-to-integer
conversion is a separate operation and is undefined for NaN, infinity, or a
value outside the destination range. Raw representation casts remain outside
the model. Constant float-to-integer casts are accepted only when the
truncated value is finite and representable; NaN, infinity, out-of-range
values, and nonconstant float-to-integer casts remain explicit
unsupported/type-error outcomes when their definedness checks are not
established; symbolic conversions carry those checks as proof obligations.

The integer constant `0` is the supported null pointer constant. C0 converts
it to the canonical null pointer when returning or initializing a pointer,
assigning a pointer local or field, passing a pointer argument, and comparing
a pointer with zero. Nonzero integers do not implicitly convert to pointers;
this is not a general integer-to-pointer conversion or cast facility. The
only other route from an integer to a pointer is an explicit cast of a 64-bit
value that is exactly the recorded address of an object pointer; see the
pointer/integer cast entry below and the memory model's treatment of pointer
addresses.

C0 follows the modeled LP64 C integer-constant rules. An unsuffixed decimal
literal has type `int32` when it fits and otherwise `int64`; an unsuffixed
octal or hexadecimal literal tries `int32`, `uint32`, `int64`, and `uint64` in
that order. `U`, `L`, and `LL` suffixes select the corresponding modeled
unsigned or 64-bit candidates. Unary `-` is applied after the positive token
has been typed, so `-2147483648` is an `int64` expression while
`-0x80000000` is an unsigned 32-bit expression with modulo arithmetic.

`sizeof` has type `size_t`, modeled as `uint64` under LP64. When both operands
of a scalar operator are arithmetic, C0 applies integer promotions and the
usual arithmetic conversions before evaluating the operation. The same rule
selects and converts both arms of an arithmetic conditional expression; only
the selected arm is evaluated. Unsupported conditional pointer combinations
are rejected with a source-positioned diagnostic.

Boolean objects use C0's one-byte LP64 layout and always contain the normalized
values `0` or `1`. Assignment, initialization, parameter passing, returns, and
casts to `bool` or `_Bool` convert integer values by zero-testing and convert
pointers by null-testing. Boolean rvalues undergo the usual integer promotion
to `int32` before arithmetic, comparisons, shifts, and bitwise operators;
comparisons and logical operators still produce `int32` results. Pointers to
boolean objects and boolean pointer arithmetic are not currently modeled.

## Supported expressions and statements

Supported C0 surface includes:

- ordinary `//` line comments and `/* ... */` block comments
- decimal, octal, and hexadecimal integer literals, with the conventional
  `U`, `L`, and `LL` suffixes (including their standard combinations), and
  variables
- named enum constants from supported declarations
- negative integer literals and unary `-`; leading-zero literals use C's octal
  syntax, and the positive token's C type is retained before negation
- unary `+` for scalar expressions
- scalar casts `(int16) expression`, `(int32) expression`, `(uint8) expression`,
  `(uint16) expression`, `(uint32) expression`, `(int64) expression`, and
  `(uint64) expression`; supported widening conversions preserve the value,
  while conversion from a signed or unsigned 64-bit integer to `uint32`
  retains the low 32 bits (modulo 2^32), including for symbolic values.
  Other narrowing requires a concrete representable value or a checked target
  range where the conversion is modeled (`int16`: `-32768..32767`, `uint8`:
  `0..255`, and `uint16`: `0..65535`), while aggregate casts remain outside C0
- the GNU type operators `typeof(type-name)` and `__typeof__(type-name)`, plus
  their expression forms `typeof(expression)` and `__typeof__(expression)`;
  expression operands are inspected only for their modeled C0 type and are not
  evaluated, including when they contain a call. The result preserves the
  modeled scalar or pointer type, struct-pointer tag, and supported `const`
  qualification. Unsupported or unmodeled operand types are rejected
- pointer/integer casts under the LP64 profile: `(unsigned long) p` (or any
  64-bit integer type) converts an object pointer to its address, an integer
  term that keeps the exact source pointer; `(struct T*) word` converts back
  when the word is such an address plus a tag proven zero (after masking, or
  by a fact), or zero, restoring the original pointer and its provenance.
  Tag operations `word + t`, `word | b`, `word & ~m`, and `word & m` on such
  a word are checked against the pointer's `aligned` evidence. Narrower
  integer targets, function pointers, and integers with no originating
  pointer are rejected
- object-pointer casts between a modeled typed pointer and `void *`, preserving
  the source pointer's provenance and pointer qualifiers; the opaque result
  may be compared or passed onward, but not dereferenced or used in arithmetic
- constant casts between integer, `float`, and `double` values; integer-to-float
  and float-width conversions use round-to-nearest, ties-to-even, while
  float-to-integer conversion truncates toward zero and requires a finite,
  representable source value
- same-width floating arithmetic with `+`, `-`, `*`, and `/`; operations use
  the declared result width, preserve signed zero and infinities, produce
  canonical NaNs for invalid IEEE operations, and never use integer overflow
  or division-by-zero behavior
- decimal floating literals, `INFINITY`, `NAN`, `INFINITYF`, and `NANF`, plus
  `isfinite`, `isinf`, `iszero`, `issubnormal`, and `isnan` for constant or
  symbolic float/double expressions
- ASCII byte character literals such as `'x'`, `'\n'`, and `'\0'`
- signed `+`, `-`, `*`, `/`, and `%`
- `uint32` `+` and `-` with 32-bit modular results
- `uint32` `*`, `/`, and `%` with modular multiplication, unsigned division
  and remainder, and division-by-zero undefined behavior
- `int16`, `int32`, `uint8`, and `uint16` rvalues promote to `int32` before
  arithmetic, comparisons, shifts, and bitwise operators
- `int64` and `uint64` arithmetic, comparisons, bitwise operators, and shifts
  retain their eight-byte signed or unsigned semantics; signed arithmetic keeps
  its overflow obligations and unsigned arithmetic wraps modulo 2^64
- `size_t` is the modeled LP64 `uint64` type and can be used for scalar
  arithmetic and array or pointer indices
- mixed arithmetic operands use C's integer promotions and usual arithmetic
  conversions; arithmetic conditional arms are converted to their common type
- `int32` and `uint32` shifts `<<` and `>>`; unsigned right shifts are logical,
  and shift results use the promoted left operand's type
- `uint32` bitwise `&`, `|`, `^`, and unary `~`
- `int32` bitwise `&`, `|`, `^`, and unary `~` with fixed 32-bit
  two's-complement bitvector semantics
- signed comparisons and equality, with C's precedence: `==` and `!=` bind
  more loosely than `<`, `<=`, `>`, and `>=`, so `a == b < c` is
  `a == (b < c)`
- C logical `&&`, `||`, and unary `!` with short-circuit C scalar truthiness
- the scalar conditional operator `condition ? then_expression : else_expression`
  with the usual arithmetic conversion of arithmetic arms and short-circuit
  branch evaluation
- assignment, sequencing, empty blocks, and empty `;` statements
- scalar declaration initializers such as `int32 i = 0;`, and scalar array
  initializers such as `int32 values[3] = {1, 2, 3};` or nested
  `int32 matrix[2][3] = {{1, 2, 3}, {4, 5, 6}};`
- same-type local declaration lists such as `int32 i = 0, j = 1;`, with each
  declarator lowered in source order
- function-local scalar `static` declarations and fixed or inferred
  scalar `static` arrays such as `static int32 calls = 0;` and
  `static int32 values[3] = {1, 2};`; the object is initialized once at
  function entry, retains its stable address across calls, and may be named by
  the owning function's contracts
- basic ASCII string literals with the supported escapes; each literal is a
  NUL-terminated read-only `uint8` array whose pointer can be returned,
  indexed, and passed through the existing byte-buffer interfaces
- scalar statement update sugar: `x++`, `x--`, `++x`, `--x`, `x += expr`, `x -= expr`,
  `x *= expr`, `x /= expr`, `x %= expr`, `x <<= expr`, `x >>= expr`,
  `x &= expr`, `x |= expr`, and `x ^= expr`; the same read-modify-write forms
  are supported for indexed and field lvalues such as `a[i] += expr` and
  `p->count++`, with the lvalue address evaluated once
- `if` with an optional `else`, using C scalar truthiness; each arm may be a
  single statement, so ordinary `else if` chains are accepted
- `switch (expression)` with a compound body whose direct labels are integer
  or character literals and at most one `default`; execution starts at the
  selected label and falls through later cases in source order, while `break`
  exits the switch
- `while` with either a compound body or one controlled statement; `break`
  exits the innermost `while`, and `continue` skips to its next condition check
- `break` exits the innermost `while`, `do ... while`, or `for` loop; `continue`
  skips to the next condition check in `while` and `do ... while`, and executes
  the `for` step before its next condition check
- `do ... while` loops with either a compound body or one controlled statement,
  executing the body once before its first condition check; `break` exits the
  loop and `continue` proceeds to the post-test condition
- assignment-style `for (init; condition; step)` loops lowered to `while`,
  including an omitted condition (equivalent to true),
  with either a compound body or one controlled statement; the step may be a
  comma-separated sequence of scalar assignments or updates, and the
  initializer or step may be omitted; scalar assignment initializers and
  same-type declaration initializers may also be comma-separated
- `return`
- bare `return;` and ordinary fallthrough from `void` functions
- address-of lvalues, including direct and nested modeled scalar leaf fields
  and indexed cells in fixed-dimensional scalar-array fields
- pointer addition and indexing for every modeled data-pointer type, scaled by
  the pointee width; `size_t`, `int64`, and `uint64` indices retain their
  64-bit value while forming the pointer offset
- pointer-array arithmetic for every modeled `T**`, scaled by the LP64
  eight-byte pointer pointee
- pointer loads and stores, including pointer-valued cells through `T**`
- `p[i]` indexing for all modeled scalar pointers
- pointer-array indexing such as `p[i]` for every modeled `T**`
- row-major indexing for multidimensional scalar local arrays
- one-dimensional array parameters of supported structs, with `items[i].field`
  accesses using the complete ABI struct stride
- heap arrays of supported structs, allocated with `malloc` or `calloc` using
  `count * sizeof(struct T)` and resized with bounded `realloc`; indexed
  `items[i].field` accesses use the complete ABI struct stride
- a small struct slice: `struct name { ... };`, `struct name*` and
  `struct name**` pointers, chained `p->child->field` loads/stores for scalar
  fields and pointer fields, and address-taking of struct-pointer cells such
  as `&p->child` for `struct name** link; *link = replacement;`
- local arrays of the supported struct shapes, with indexed `items[i].field`
  loads and stores using the struct's LP64 stride
- known function calls through the current function environment, either
  assigned, used as standalone statements when the result is discarded, or
  embedded in an unconditional expression; expression calls lower to fresh
  temporaries and checked `CallAssign` statements; body-less C callees may be
  declared as `extern` contracts in the sidecar. If lowering rejects an
  unsupported call combination, the diagnostic points to the original call
  expression rather than the synthesized temporary.
- multiple C function definitions and forward prototypes in one verifying
  source
- file-scope scalar definitions for the modeled integer, floating-point, and
  data-pointer types, with literal, null-pointer, or address-constant
  initializers (or zero initialization); compatible
  `extern` declarations may be shared through project-local headers, and the
  linker requires exactly one externally linked definition across the verified
  source bundle. File-scope `static` definitions use private storage for their
  own source file, so same-named statics in different files are independent;
  `const` scalar objects and scalar tables use stable read-only storage
- fixed-size file-scope arrays of those scalar types, including fixed
  multidimensional scalar arrays, with bounded integer constant-expression or
  zero-filled initializers; compatible `extern` array declarations may be
  shared through project-local headers, and file-scope `static` arrays use
  private storage for their own source file
- project-local quoted `#include "header.h"` declarations supplied in the
  verifying source bundle; headers may contain supported type declarations,
  prototypes, and `static inline` or `static __always_inline` function bodies.
  Those helpers may carry the allowlisted declaration-only GNU spellings
  `__attribute__((always_inline))` or `__attribute__((__always_inline__))`
  before the return type or after the parameter list. Inline helpers are checked
  from their expanded C bodies at each call site, on the caller's own memory
  and resources, and receive translation-unit-local
  kernel identities: each verifying `.c` file gets its own instance of a
  shared header helper, named `{helper}#inline:{translation-unit}` in
  diagnostics that carry the kernel identity. A sidecar contract may also name an inline helper by its
  ordinary C spelling for direct verification; calls still execute the body
  rather than applying that contract as a call boundary. Parse diagnostics
  for bundle sources name the bundle file and line behind the expanded
  text, so an error inside a header helper points at `header.h:line`.
  Linkage and body-selection rules, for the single supported
  `x86_64-linux-kernel` compiler profile: every call to a supported
  `static inline` or `static __always_inline` helper executes the header
  body at the call site. Click never emits a standalone out-of-line
  definition, never selects an external definition, and never applies a
  sidecar contract as a call boundary; this matches the observable
  behavior of `always_inline` helpers under the supported profile for the
  C0 subset. `extern inline`, bare `inline` without `static`, and other
  inline spellings have profile-dependent emission rules and remain
  rejected. Canonical whole-header guards
  using `#ifndef NAME`/`#define NAME`/`#endif` and `#pragma once` are supported,
  so a shared header may be reached through multiple include paths without
  being expanded twice; other function definitions in headers remain
  unsupported
- object-like macros in C sources and local headers, including integer and
  string literals, keyword aliases, and multi-token expressions; these are
  rescanned for exact identifier uses in translation-unit order. Comments in
  replacements become whitespace; quoted text is preserved. Backslash-newline
  continuation is processed before comments and directives. `#undef NAME`
  removes a macro from later expansion and conditions.
- one- to three-parameter function-like macros in C sources and local headers,
  such as `#define ADD(left, right) ((left) + (right))`; calls use ordinary
  argument substitution, parse balanced nested arguments, and rescan the
  replacement for other supported macros. Macro recursion, more than three
  parameters, empty arguments, stringification, and token pasting remain
  unsupported. Expansion is limited to depth 64 and one megabyte per expanded
  line or replacement, with a four-megabyte cumulative scan-work limit
- bounded conditional compilation using `#if 0`, `#if 1`, `#if NAME` for a
  previously defined 0/1 literal macro, `#ifdef NAME`, `#ifndef NAME`,
  `#if defined(NAME)`, `#if !defined(NAME)`, and those atoms combined with
  `!`, `&&`, `||`, or parentheses; `#elif`, `#else`, and `#endif` are also
  supported. Equality and inequality comparisons (`==` and `!=`) are supported
  between integer or character literals, literal-valued macros, and
  `defined(NAME)`, and can be combined with those boolean operators. Undefined
  identifiers evaluate to zero, including after `#undef`. Arithmetic,
  relational operators, and other general preprocessor expressions remain
  unsupported
- the modeled system headers `#include <stdint.h>` and `#include <inttypes.h>`, which contribute the
  standard spellings already mapped to C0 types, including `int32_t` and
  `uint8_t`; they are otherwise no-ops. This does not model format macros or
  library functions from `<inttypes.h>`
- function-pointer callbacks for modeled signatures, using `&function` to
  form a callback and a function-pointer local or parameter as an indirect
  call target. A bare function designator decays to that same address wherever
  a value is expected, so `apply(compare, 40, 2)` and `apply(&compare, 40, 2)`
  pass the same callback; the name must be declared as a function in the
  translation unit that uses it, and a name in call position stays a call.
  Callback signatures may include modeled `struct T *` and
  `struct T **` parameters and returns; C0 retains those nominal tags and
  rejects a known callback target with a different struct identity before
  lowering. An indirect call whose exact target is known dispatches that
  function. A call through an abstract function-pointer parameter or an
  unknown field value is rejected until it has a checked named contract;
  Click does not infer behavior by enumerating same-signature project
  functions. Function pointers are not dereferenceable or subject to pointer
  arithmetic
- GNU statement expressions of the exact form `({ statements; value; })`;
  `statements` use the supported C0 statement grammar and execute in a nested
  scope, while the final `value` must be a modeled scalar, pointer, or function
  pointer expression. The body and final value are lowered into an explicit
  temporary in source order, preserving assignments and calls; `return`,
  `break`, and `continue` inside the statement expression remain unsupported
- the optimization-only GNU builtin `__builtin_expect(value, hint)`, with
  exactly two integer operands. It evaluates and returns `value` unchanged;
  `hint` must be an integer expression without a modeled runtime effect. Other
  `__builtin_*` calls are rejected rather than silently treated as ordinary
  functions
- `sizeof` for supported scalar and pointer types, and
  `malloc(sizeof(struct T))` or `malloc(count * sizeof(struct T))` assigned to
  a matching `struct T*`, runtime-sized
  `int32` backing allocation such as `malloc(count * sizeof(int32))`,
  width-preserving allocation for the other modeled scalar pointer types,
  byte-oriented `uint8` backing allocation such as `malloc(count * sizeof(uint8))`,
  pointer-array allocation such as `malloc(count * sizeof(int32*))` or
  `malloc(count * sizeof(uint64*))` assigned to the matching `T**`, arbitrary
  positive byte extents assigned to supported pointer types, zeroed
  runtime-sized scalar allocation such as `calloc(count, sizeof(int32))`,
  matching zeroed struct allocation such as `calloc(count, sizeof(struct T))`,
  bounded `realloc(data, bytes)` for live modeled scalar pointers, pointer
  arrays, and matching `struct T*` allocations, including arbitrary byte
  extents; initialized cells are preserved only when their complete byte
  ranges fit, and standalone `free(pointer);`
- local scalar, pointer, and fixed-size array declarations for the modeled
  integer and floating-point types, plus the supported struct shapes
- struct-value declarations, assignments, parameters, and returns for the
  supported scalar, data-pointer, fixed-array, and embedded-struct shapes; each
  value has independent storage and may be accessed with `value.field`

Comparisons return C-style `int32` values: `0` or `1`. They are not Click
propositions by themselves. `bool`, `int16`, `uint8`, and `uint16` rvalues
promote to `int32` for arithmetic, ordered comparisons, shifts, bitwise operators,
assignments, and returns.
`uint32` equality compares 32-bit values directly and its ordered comparisons
use unsigned order. Its addition, subtraction, and multiplication wrap modulo
2^32; division and remainder use unsigned operands. Its shifts preserve the
promoted left operand's type, with logical right shift for `uint32`. Assigning or
returning an `int32` into `int16`, `uint8`, or `uint16`, including an explicit
cast, requires Click to prove the corresponding target range. Conditional
expressions first convert arithmetic arms to their common C type, then evaluate
only the selected branch.

C0 follows the GCC/Clang/MSVC consensus for signed right shift: `int32 >> k`
is arithmetic right shift with sign extension. This is implementation-defined
in ISO C for negative signed values, but it is the behavior of the mainstream
compilers Click is targeting.

## File-scope scalar globals

Click models a supported file-scope scalar definition as one program object.
For example, `int32 counter = 3;` defines `counter`, while
`extern int32 counter;` declares the same object for another translation unit.
A source selected by `verifying` may contain only data declarations and
definitions; it does not need a function body. These objects participate in
the same bundle linking and conflict checks as objects in function-bearing files.

Definitions without an initializer are tentative definitions and start at zero;
repeated compatible tentative declarations coalesce, including across
translation units, and one initialized definition supersedes them. Multiple
initialized definitions remain rejected. Integer scalar initializers
may use bounded constant expressions built from supported integer literals and
arithmetic, bitwise, shift, comparison, logical, and conditional operators,
plus checked scalar integer casts, with the same usual arithmetic conversions
and unsigned wrapping as runtime expressions. Signed and narrow target types
still require a representable final value.
<!-- verified-example: mdtests/c_expression_typing.md -->
Logical and conditional expressions evaluate only the branch selected by their
constant condition. Pointer initializers may use the null pointer constant `0` or the address
of a declared scalar object. Address constants retain the target's stable
global or function-qualified static block identity, including when a pointer is
used through a `const`-qualified pointee view. Floating-point initializers
remain literal-only, and other dynamic expressions remain unsupported.
File-scope `static` definitions have internal linkage and are
private to their
translation unit. Fixed-size scalar arrays use the same linkage rules,
including coalesced compatible tentative declarations and one initialized
definition across translation units. One-dimensional arrays are initialized
element-by-element (omitted elements are zero) and accept constant-expression
values plus literal index designators such as `[2] = 7`. Fixed multidimensional
scalar arrays use nested positional initializer groups, preserve their
declared shape, and flatten indexes row-major into the same stable element
block. Extern and tentative definitions must agree on every complete
dimension; an omitted outer dimension must retain compatible inner bounds.
All
scalar arrays expose their array-to-pointer address for indexed expressions and
contract footprints; contract ranges refer to the flattened storage block.
Fixed-size one-dimensional arrays of supported scalar-field structs use the
same stable linkage and ABI-sized element stride; incomplete, non-literal,
or dynamically initialized arrays remain outside this slice. An external
declaration or external-linkage tentative definition may omit its outer bound,
as in `extern int32 table[];`, `extern int32 matrix[][3];`,
`int32 values[];`, or `int32 matrix[][3];`; bundle linking resolves it against
one complete fixed-size definition in the source bundle, preserving any
declared inner bounds. An external-linkage multidimensional definition may
also omit its outer bound when nested positional initializer groups infer it,
as in `int32 matrix[][3] = {{1, 2}, {3, 4, 5}};`. A file-scope `static`
multidimensional definition with a nested positional initializer may likewise
omit its outer bound; the resulting storage remains private to its translation
unit. An
unresolved incomplete tentative definition and a file-scope
`static` incomplete array without a complete definition in the same
translation unit remain unsupported. A scalar definition may also
infer its bound from a non-empty positional initializer, as in
`int32 values[] = {1, 2, 3};`; the resulting object is the same fixed-size
array model. Empty initializers, flat or designated initializers for inferred
multidimensional arrays, file-scope `static` incomplete multidimensional
declarations without initializers, array designators on multidimensional arrays,
and aggregate arrays still require an explicit one-dimensional form or remain
unsupported.
String literals are described below.

Every function sees the linked object through its stable address. Contracts
name the scalar value directly, and name its one-cell memory footprint with
`owns &counter[0..1]`.
`old(counter)` refers to the value in the function-entry memory snapshot.
Global writes therefore participate in ordinary contract certification and are
visible to later calls in the same verified execution.

A file-scope `static int32 counter = 0;` is a separate object in each source
file that defines it. The owning source file's functions can name it in
contracts and authorize its one-cell footprint with `owns &counter[0..1]`.
It cannot satisfy an `extern` declaration in another translation unit, and
file-scope static definitions are not allowed in declaration-only headers.
Static-storage pointers may likewise be initialized from the address of a
declared scalar object, an array element, or a scalar struct field. The target
address is materialized from the containing object's stable block plus its ABI
byte offset; function-local static pointers retain that address across calls.

Struct objects whose layouts contain only supported scalar fields are also
available with zero initialization, for example `struct state shared;` and
`extern struct state shared;`. An externally linked definition is shared by
all translation units, while `static struct state private;` gets private
translation-unit storage. The object is modeled as typed leaf fields rather
than as a scalar value, so contracts authorize the fields they write with
footprints such as `owns shared.value[0..1]`; `old(shared.value)` refers
to the field's entry value. Positional initializers containing compile-time
scalar or null-pointer literals are supported for these aggregates as well;
omitted leaves retain zero initialization. A declaration such as
`struct state entries[2] = {{1}, {3, 1}};` provides the same field access
through `entries[1].value` and `entries[1].ready`, with each element advancing
by the complete ABI struct size. Static-storage designated initializers select
scalar fields with `.field = literal`; designated fields may appear in any
order and omitted leaves retain zero initialization. One-dimensional arrays of
these aggregates also accept `[literal] = {...}` element designators, with
omitted elements zero-filled. Non-literal designator expressions, designated
initializers for inline scalar arrays, multidimensional aggregate arrays,
uninitialized incomplete aggregate definitions, and dynamic or non-literal initialization
remain outside this slice. An `extern struct state entries[]` declaration is
supported when bundle linking finds a complete fixed-size definition.
One-dimensional aggregate definitions may infer their bound from non-empty
positional element groups, such as `struct state entries[] = {{1}, {3, 1}};`.
This also applies to file-scope and function-local `static` arrays. Element
designators still require an explicit bound.
Definitions without an initializer are tentative: compatible tentative
declarations coalesce across translation units, and one initialized definition
supersedes them for both aggregate objects and aggregate arrays. Multiple
initialized definitions or incompatible aggregate types remain rejected.

For example, `int32 table[3] = {1, 2};` creates a three-element array whose
third element starts at zero. Contracts name its elements directly and its
memory range with `owns table[0..3]`; the range uses array elements rather
than physical bytes. An `extern int32 table[3];` declaration refers to that
same storage from another source file. A `const int32 table[3] = {1, 2};`
instead creates the same stable table with read-only backing storage. Reads
through `table` are allowed across translation units, and a parameter such as
`const int32 *values` preserves the read-only view: indexing it is a load, but
storing through it is rejected. Qualification-only casts preserve pointer
provenance; they do not grant a writable view.

Const-qualified struct globals and function-local static struct objects and
arrays use the same stable aggregate storage with read-only backing. Their
fields can be read normally, but assigning to a field is rejected. An
`extern const struct state shared;` declaration must match the linked
definition's const qualifier. The exact Linux-style trailing struct attribute
`__attribute__((aligned(sizeof(long))))` (and `__aligned__`) is also modeled as
an LP64 eight-byte alignment requirement, including its effect on nested field
offsets and tail padding.

## Sequential scalar and pointer-qualified volatile objects

C0 supports a deliberately small sequential volatile model for scalar integer
objects, pointers to scalar storage, and pointer-valued objects. A leading
qualifier such as
`volatile int32 status;` qualifies the object, while
`volatile int32 *status_ptr;` qualifies the scalar storage reached through the
pointer. `int32 * volatile slot;` instead qualifies the pointer object itself,
and `int32 * volatile *slot_cell;` qualifies the pointer-valued cell reached
through `slot_cell`. These qualifiers are tracked independently. Each direct
or pointer-derived read or write emits a distinct, ordered kernel-certified
execution fact, so the verifier cannot silently cache the access or erase it
while checking the surrounding expression or statement. The value still comes
from the current symbolic memory state; this slice does not model external
agents changing memory between accesses.

Taking the address of a supported volatile object and accessing it through
`*p` or `p[i]` are supported, including sequential stores shaped like Linux
`WRITE_ONCE` pointer-cell updates. Qualifiers below the immediate pointee,
volatile struct or union storage, volatile array objects, volatile struct
fields, and volatile function-pointer objects remain rejected. Threads,
atomics, fences, signals, and device protocols are a separate
concurrency-dependent problem tracked in
`issues/concurrency-and-atomics.md`.

## Checked sequential kernel access primitives

C0 recognizes the Linux-style `READ_ONCE`, `WRITE_ONCE`, `likely`, `unlikely`,
and `rcu_assign_pointer` spellings at the source boundary. Header wrappers
whose replacement text uses GNU `typeof`, volatile accesses, or the matching
helper names are mapped to these checked operations before ordinary C0
parsing, so statement-expression implementations do not get erased or
silently treated as ordinary calls.

`READ_ONCE(x)` reads one supported scalar or object-pointer lvalue and
`WRITE_ONCE(x, value)` writes one such cell. Both evaluate their lvalue and
value operands once; the latter is expression-valued and preserves the stored
value. `rcu_assign_pointer(p, value)` is the statement-form pointer-cell store
used by the sequential profile. `likely(x)`, `unlikely(x)`, and
`__builtin_expect(x, constant)` preserve the value and effects of `x`; the
prediction is not a proof assumption.

Each supported access emits a distinct ordered sequential access event and
updates the checked symbolic memory state. Pointer values retain their C0
type and allocation provenance. These events do not assert atomicity,
inter-thread visibility, release/acquire ordering, RCU grace periods, or the
absence of data races, and they cannot discharge a contract requiring any of
those properties. The selected sequential profile rejects atomic, fence,
release/acquire, and other concurrency-only builtins instead of assigning
them sequential meanings.

The primitive projection is limited to the modeled scalar and object-pointer
cells. It does not extend the separate restrictions on volatile pointer-valued
objects, volatile aggregates, or unsupported qualifier depth.

## Function-local scalar statics

A function may declare a supported scalar with `static`, for example
`static int32 calls = 0;`, or a scalar array with fixed or inferred bounds, such
as `static int32 values[3] = {1, 2};`. The declaration is initialized once when
its function-qualified storage first enters the symbolic state; later calls and
recursive frames reuse the same object. An omitted initializer means zero,
and explicit integer initializers use the same bounded constant-expression
subset as file-scope globals. Array initializers are applied
element-by-element, and omitted trailing elements are zero-filled.
Adding `const` to a supported static scalar or scalar table gives it the same
stable function-qualified storage with read-only backing memory; mutation of
the object remains rejected.

The owning function's contracts can name a scalar static directly and authorize
its one-cell writes with `owns &calls[0..1]`. Array statics are named by
their elements and authorize their storage with a range such as
`owns values[0..3]`; `old(values[i])` refers to the function-entry value of
that element. A static struct can use a positional or designated compile-time
initializer, such as `static struct state state = {.value = 3, .ready = 1};`;
omitted fields become zero and the object still uses stable function-qualified
storage. A static array of structs can use nested positional groups or literal
element designators, such as `static struct state states[2] = {[1] =
{.value = 5, .ready = 1}};`, and its indexed fields can be named in
ownership clauses such as `owns states[1].value[0..1]`. These designated forms apply to
static-storage aggregates; automatic/local aggregate values and arrays remain
positional-only. Scalar static arrays support fixed multidimensional shapes
and an omitted outer bound inferred from non-empty nested positional rows.
One-dimensional scalar static arrays may also infer their bound from non-empty
positional initializers. Multidimensional aggregate arrays, uninitialized
incomplete arrays, non-literal
designators, and dynamic or non-literal initialization remain unsupported.

## String literals

C0 accepts basic ASCII string literals in expressions, such as `"ok\\n"`.
Adjacent basic literals are concatenated as in C, so `"hello, " "world"`
creates one literal object.
Supported escapes are `\\n`, `\\r`, `\\t`, `\\0`, `\\\\`, `\\'`, and `\\"`.
Each literal sequence is represented as a fresh function-owned `uint8` array with one
explicit trailing NUL byte. The expression has the array-to-pointer behavior of
a local byte array, so the result can be returned, indexed, or passed to a
function expecting `uint8*`. The storage is stable across calls and remains
read-only even after the pointer is copied to another local; an indirect store
through that pointer is undefined behavior. The existing `loadable` byte-range
interface can describe reads from the literal. Wide literals, concatenated
literals, non-ASCII characters, and unsupported escapes remain outside C0.

## Named function contracts

Named contracts may explicitly separate proof parameters from the C signature:

<!-- verified-example: mdtests/contract_resource_parameters.md -->
```click
contract Read(cell: marked_cell(p)) for int32(int32* p) {
    owns cell;
    ensures cell.revision == old(cell.revision);
}
```

The resource is declared in the linked fixture. The first parameter list
declares proof-side resource handles. The signature after `for` describes the
C call and supplies `p`. `owns cell` requires and returns ownership; the
parameter declaration alone grants none. Resource bindings in this form must
appear in the explicit parameter list, not be introduced implicitly in the
body. Default arguments are not supported.

An application supplies positional resource names, as in
`step(Read(first))`. The caller must bind `first` through named ownership.
Missing arguments, wrong resource families, and duplicate exclusive arguments
are rejected. Explicit callback applications transport opaque instances and
check their resource arguments against the actual C arguments. Returned
instances keep their identities but get fresh symbolic fields; only explicit
guarantees relate those fields to the call-entry values. Unselected instances
remain framed. Concrete function refinement for these parameterized contracts
and ordinary inline-call instance transport are not yet supported.

Empty applications are supported end to end:

<!-- verified-example: mdtests/contract_explicit_empty_application.md -->
```click
contract Identity() for int32(int32 x) {
    ensures result == x;
}
```

Use `step(Identity())` to select that contract. The C argument `x` comes from
the C call, not from the proof application. The older C-signature-only
declaration and `step(Identity)` selection syntax remain supported for older
contracts; contracts declared with the new parameter-list syntax require an
explicit application when selected by name.

A top-level `contract` block defines a reusable behavioral interface without
declaring a concrete C function:

<!-- verified-example: mdtests/c_named_function_contract.md -->
```click
contract int32 Comparator(int32 left, int32 right) {
    requires 0 <= right;
    requires right <= left;
    ensures result == left - right;
}
```

Applying the contract name as a proposition attaches that interface to one
function-pointer value:

<!-- verified-example: mdtests/c_named_function_contract.md -->
```click
int32 apply(int32 (*callback)(int32, int32), int32 left, int32 right) {
    requires Comparator(callback);
    requires 0 <= right;
    requires right <= left;
    ensures result == left - right by auto;
}
```

At the indirect call, Click looks up contracts indexed by the exact symbolic
pointer. It checks the named preconditions, applies the postconditions,
resource transition, and owned footprint through the ordinary
verified-call rule. It does not enumerate project functions or infer behavior
from a matching C signature. Contract applications are type-checked against
the complete modeled function-pointer signature.

When several named contracts are known for the same symbolic pointer, their
preconditions are checked against the same pre-call state. Contracts whose
requirements cannot be established do not contribute guarantees. If none
applies, the call fails with a precondition or resource diagnostic. Argument
evaluation is shared, and applicable resource-free interfaces
constrain one result rather than creating separate execution paths. For
example, a lower bound and an upper bound can jointly establish result equality.
Separate calls still have separate symbolic results.

If exactly one interface applies, it uses the ordinary resource transition and
owned footprint. When several resource interfaces apply, write
`step(Buffered)` to choose the named contract for the function-pointer call at
the current frontier. The contract must be known for that exact pointer and
signature, and its requirements must hold; an invalid choice never falls back
to another contract. The choice applies to this step only and is retained in
the checked proof and its expansion. It cannot select a contract for a plain
direct function call, or advance a non-call statement.

The selected contract supplies the single resource transition and owned
footprint. Other applicable interfaces retain their resource-independent scalar
and sequence guarantees over that same result and memory, including supported
`old` memory expressions. Resource-dependent clauses, such as conditions on
`count`, belong to the selected model; they are not interpreted using another
model's ledger. Alternative ownership is never added as a second spendable
copy. Use ordinary `fold` and `unfold` to change representation afterward.

Forming `Comparator(&compare)` checks the verified (or explicit external)
contract of `compare` against the named contract. Parameter names are binders
and need not use the same spelling, and the formed fact is indexed by the
concrete address `&compare`. The check is behavioral refinement: the named
preconditions must imply the concrete function's preconditions, and the
concrete function's postconditions, together with the named preconditions,
must imply the named postconditions. A contract like `Comparator`, whose
clauses read no memory, needs nothing further. The proposition classes
formation admits and excludes, the extra resource conditions a memory-reading
clause carries, the exactness rule it follows, and the pairing it needs for a
contract with resource proof parameters are in
[Automatic formation at `&f`](index.md#automatic-formation-at-f).

A refinement outside that route is stated as a closed pure theorem, whose proof
spells the step with `both`, `left`/`right`, `intro`, `extract`, `rewrite`, or
`contradiction`, and `click expand` prints the spelling. `apply` the theorem
before the call that needs the contract.

When refinement depends on a conditional footprint, state it as a closed pure
theorem. The conclusion applies the named contract to one concrete function
address. `unfold(Contract)` introduces arbitrary values for the contract's
call parameters, after which an ordinary proof can use explicit logical cases:

<!-- verified-example: mdtests/c_named_function_contract_refinement_theorem.md -->
```click
theorem set_one_is_make_positive() {
    ensures MakePositive(&set_one_if_active) by {
        unfold(MakePositive);

        if active != 0 {
            simp();
        } else {
            simp();
        }
    }
}
```

The theorem is reusable like any other proved theorem; `apply` can introduce
its contract fact before passing the concrete pointer to a higher-order
function. After opening the contracts, the body uses the ordinary
non-execution proof engine: `have`, theorem application, rewriting,
quantifier tactics, and logical cases work as in other proposition proofs.
There is no execution frontier, so execution tactics are unavailable.
The kernel constructs the arbitrary call states and checks resource/effect
compatibility; the proof establishes the requirement and guarantee
implications. It does not inspect unrelated project functions or enumerate
combinations of footprint guards.

The same proof may explicitly open stateful predicates used by either
interface. After the contract itself is open, `unfold(Predicate)` authorizes
the registered, checked definition of every occurrence of that predicate in
the local comparison. This remains an explicit proof step: direct function
pointer formation does not unfold a predicate whose opaque interface differs,
and naming an unrelated predicate grants no authority. Ordinary `simp` may
select a needed predicate unfolding and record it in its certificate. The
unfolded body uses the same symbolic entry and post-call memories as ordinary scalar refinement,
including `old` arguments. Predicate unfolding composes with written `if`
cases, helper facts, and other ordinary logical tactics.

Refinement also accepts finite sequence literals, concatenation, equality,
inequality, and membership whose elements use supported scalar expressions
over current or `old` memory. Integer sequence equality supplies its element
equalities to the local proof; concatenation preserves element order. For
example, a callback that reverses a pair refines an interface permitting
either the original pair or its reversal. Entry and post-call values remain

Memory, abstract-token, and folded-composite resource transitions
support framing and scoped borrowing. Click uses
the named input resources to supply the concrete function's requirements,
preserves everything the concrete function only borrows or does not need as
an inferred frame, and requires the concrete guarantees plus that frame to
provide the named guarantees. Thus a concrete callback may own a smaller
constant or symbolic subrange, or borrow a smaller view from named ownership.
It may not require ownership when the named contract supplies only a view, or
omit ownership the named contract promises to return. The same rule frames
unused abstract tokens and lets concrete callbacks borrow tokens that the
named contract owns. Folded composites follow the same rule as opaque
capabilities. Token and composite names and arguments retain exact identity;
refinement does not unfold a composite to search for matching children.
Symbolic owned quantities use the same inferred-frame rule for abstract tokens
and nonrecursive folded composites. If the named preconditions prove that the
named quantity covers the concrete requirement, refinement subtracts the
concrete quantity as one symbolic resource fact, frames the remainder, and
recombines it with the concrete output. It never enumerates individual units.

Each concrete owned range must be provably contained in a named range. When
conditional resources infer guarded ranges, the concrete guard must imply the
named guard under the named preconditions. Thus an unguarded named range
accepts a guarded concrete range, and a concrete callback may omit a guarded
range entirely; an unguarded concrete range does not fit a guarded named range
unless the named preconditions prove that guard. A closed refinement theorem
can handle guarded post-call memory by explicitly splitting until every
concrete owned guard is decided, and can compare stateful user predicates by
explicitly unfolding their definitions. Stateful algebraic,
resource-relation, explicit-memory-snapshot, and general non-memory resource
refinement remain future work.

Named contracts may use ordinary pure `requires` and `ensures`, resource
requirements and guarantees, and `owns`/`views` clauses. They cannot
contain proof scripts, decreases clauses, or resource-construction authority.
Several distinct contract facts can be packaged in one composite resource,
borrowed through verified helper calls, and composed in an outer pipeline.

## External function contracts

A sidecar can describe a C function whose implementation is outside the
verified source set with an `extern` block:

<!-- verified-example: mdtests/external_function_contract_call.md -->
```click
extern int32 external_identity(int32 x) {
    requires x >= 0;
    ensures result == x;
}
```

The declaration may use the ordinary `requires`, `ensures`, resource, and
`owns`/`views` clauses. It must contain a contract and cannot carry a
proof script. Calls apply the declaration as an explicit opaque assumption;
Click does not execute a synthesized body or treat the declaration as proof
that an implementation was verified. A caller still has to establish every
declared precondition.

An external allocator can describe storage returned through a supported data
pointer or pointer-array type. For example:

<!-- verified-example: mdtests/external_allocator_contract.md -->
```click
extern uint8* external_alloc(int32 bytes) {
    requires 0 < bytes;
    ensures result != 0;
    produces allocation(result, bytes);
    produces result[0..bytes];
}
```

The allocation authority's base is pointer-type independent; the owned range
uses the returned pointer's logical element width. The declaration therefore
also works for any modeled data pointer, pointer-to-pointer, or supported
struct pointer result when the byte extent and owned range match that type.
This is a contract for a compatible allocator boundary, not a general
`void*`/`size_t` allocator interface.

## Undefined behavior

Signed overflow is C undefined behavior. Signed division and remainder also
have C undefined behavior for a zero divisor, and for `INT_MIN / -1` or
`INT_MIN % -1`. Shift counts must be in `0..32` for 32-bit operands and
`0..64` for 64-bit operands. Signed left shift is undefined for a negative
left operand or an unrepresentable result in the selected signed width. Proofs
involving signed arithmetic usually need requirements such as:

<!-- verified-example: mdtests/increment_requires_no_overflow.md -->
```click
requires x < 2147483647;
requires x > -2147483648;
```

Out-of-bounds memory accesses become proof obligations or undefined behavior
depending on the symbolic execution path. Prove access safety with viewed or
owned memory resources, `loadable(...)`, index bounds, and loop invariants.

Automatic scalar, pointer, and array declarations do not zero-initialize their
storage. Reading a local before a value has been written is undefined behavior.
Declaration initializers such as `int32 i = 0;` are lowered as a declaration
followed by the initializing assignment.

Scalar parameters are callee-owned objects, just like scalar locals. If a
parameter's address is taken, Click gives that parameter a distinct stack slot
for the current call, and stores through the address are visible to later reads
of the parameter by name. The slot is separate from any caller variable with
the same spelling and from slots in recursive calls. Pointer-to-pointer
parameters use 8-byte pointer cells and can be indexed and dereferenced like
ordinary C pointer arrays.

Declarations in nested compound statements may shadow parameters and locals
from an enclosing scope. C0 resolves each use to the innermost declaration
that is live at that source position, and the kernel assigns shadowed objects
distinct local identities. Their addresses and storage therefore remain
separate; after the nested block ends, a use of the outer spelling resolves to
the enclosing object again. Declarations in sibling blocks may reuse a name as
well. This lexical resolution is an import detail: Click contracts continue to
refer to the source spelling at the current proof state.

## Local arrays

Local arrays allocate stack memory blocks:

<!-- verified-example: mdtests/uint8_local_array.md -->
```c
uint8 local_byte_array() {
    uint8 a[2];
    a[0] = 'x';
    a[1] = 'y';
    return a[0];
}
```

An array name decays to a pointer rvalue for indexing and function arguments.
Direct assignment to an array object is rejected. Each modeled scalar array
uses its ABI element width (`uint8`: 1 byte, `int16`/`uint16`: 2 bytes,
`int32`/`uint32`: 4 bytes, and `int64`/`uint64`: 8 bytes). A local array
initializer writes each element in declaration order; omitted elements are
zero-initialized, and too many elements are rejected.

Scalar local arrays may have multiple fixed dimensions, such as
`int32 matrix[3][4]`. C0 lowers their storage in row-major order while
retaining the declared element width and each declared dimension. An access
such as `matrix[i][j]` therefore carries separate obligations for
`0 <= i < 3` and `0 <= j < 4` before its flattened offset is formed; the
enclosing allocation bound is not a substitute for an inner array bound.

Fixed-dimensional local arrays of copyable structs accept nested positional
element groups. Each element uses the complete ABI-sized struct stride, nested
fields are initialized recursively, and omitted fields or elements are
zero-filled.

## Struct subset

C0 supports a small struct slice:

<!-- verified-example: mdtests/struct_multifield_explicit_permissions.md -->
```c
struct owner {
    int32 len;
    int32* data;
};

int32 set_first(struct owner* owner, int32 data[]) {
    int32* current;
    owner->len = 1;
    owner->data = data;
    current = owner->data;
    current[0] = owner->len;
    return current[0];
}
```

This is intentionally not a full C struct model yet. Struct fields may be
`bool`, `int16`, `int32`, `uint8`, `uint16`, `uint32`, `int64`, `uint64`, `float`, `double`, named enum values, fixed-dimensional arrays of the
supported scalar types, or pointer-typed fields such as `int32*`, `uint8*`, `float*`, and
`struct name*`. For example,
`uint8 buf[16]` remains an inline 16-byte field; `p->buf[i]` decays that field
to a byte pointer for indexed access and does not load it as a scalar or as a
pointer-valued field. The standard spellings for the modeled scalar types are
accepted in the same positions. `struct name*` is accepted for parameters,
local pointers, and fields. Embedded struct fields whose nested declaration
precedes the containing declaration are also supported for member access. An
embedded field such as `p->inner` is an aggregate place carrying its address
and nested layout; `p->inner.value` selects the leaf field by combining the
outer and inner ABI offsets, without loading a runtime aggregate value. The
importer retains the pointee struct name across intermediate field loads, so
`p->child->field` remains typed. Named enum fields use the supported C0 ABI's
four-byte scalar representation; their enumerator names are resolved to
int32 values while the field metadata retains the enum name. Fields use the
documented LP64 ABI: each field is aligned, pointers occupy eight bytes, and
the struct size includes tail padding. Local arrays and one-dimensional
function parameters of these
supported structs retain that ABI stride for indexed field access. An array
parameter is represented as a byte-addressed pointer internally, while the
source-level index still advances by the complete struct size. Inline arrays of
embedded structs and scalar fields may have multiple fixed dimensions; indexed
leaf-field access uses each declared row-major shape, with scalar fields
advancing by their element width and embedded structs by their complete
nested-struct stride.
Pointer-backed structs may additionally declare modeled function-pointer fields.
The importer preserves each field's structural callback type, nominal struct
tags in its signature metadata, and eight-byte LP64 slot. A compatible concrete
function address can be stored in the field, loaded into a function-pointer
local, and called through that local or directly through the field expression;
an incompatible known target is rejected before lowering. A pointer-backed
field with an explicit named contract fact can be called abstractly; the fact
is associated with that exact loaded pointer rather than all fields of the
same signature.

Struct values are supported for a deliberately smaller shape: every field must
be `bool`, `int16`, `int32`, `uint8`, `uint16`, `uint32`, `int64`, `uint64`, `float`, `double`, a named enum field, a modeled data
 pointer, a modeled function pointer, a fixed-dimensional array of modeled
scalar elements, an embedded
struct whose fields satisfy the same rule, a fixed-dimensional array of such
embedded structs, or a named read-only union field. Data-pointer fields are
copied shallowly: the pointer value is duplicated, while the pointed-to
allocation remains shared. A function-pointer field copies the same way and
keeps its declared signature. A file-scope or function-local `static` object
may bind one to a function address in a positional or designated initializer,
as in `static const struct callbacks table = { .add = &add };`. A load through
a provably identified table yields that concrete address, so the indirect call
dispatches exactly that function with no contract, and writes to a `const`
table are rejected.

<!-- verified-example: mdtests/const_callback_table_dispatch.md -->
<!-- verified-example: mdtests/const_callback_table_abstract.md -->
<!-- verified-example: mdtests/const_callback_table_rejects_write.md -->
<!-- verified-example: mdtests/const_callback_table_rejects_signature.md -->

A by-value parameter,
local declaration, assignment, or return is modeled as a fresh address-backed
object and copied recursively field by field and array element by array element;
multidimensional embedded-struct arrays retain their declared shape for indexed
access and are flattened row-major into typed leaf fields for copies. Changing
a callee's ordinary fields therefore cannot mutate the caller's object, while
writes through a copied data pointer can. Direct whole-struct lvalue loads and
copies are supported for copyable structs: `dst = *src`, `*dst = *src`, and
embedded aggregate assignments such as `dst->inner = src->inner` expand into
typed leaf copies. The same address-backed form supports aggregate arguments
and returns without introducing a runtime aggregate value. Positional
aggregate initializers for copyable struct-valued locals and fixed-dimensional
local arrays of those structs use recursive typed leaf stores, preserve nested
and fixed-array shape, and zero-fill omitted members and elements. Designated
field initializers for those locals may select scalar
fields or nested embedded-struct fields in any order; omitted fields are
zero-filled. Conditional expressions over copyable structs require both branches
to have the same struct type and are evaluated lazily: the selected branch is
copied into fresh address-backed storage before assignment, argument passing,
or return. Static-storage designated initializers support scalar fields and
one-dimensional arrays of scalar-field aggregates; designated initializers for
inline scalar arrays, multidimensional arrays, and packed layout are still
unsupported. Address-taking of
modeled scalar leaf fields, including nested embedded-struct leaves and
indexed cells in fixed-dimensional scalar-array fields, preserves the field's
ABI offset and allocation provenance. Indexed inline-array fields retain the
same per-dimension subobject checks, so an index cannot spill into a following
struct field merely because the containing object is large enough. Pointer and
array forms now preserve the declared scalar width; unsupported pointer forms
remain outside the modeled subset.
Direct whole-union values and union-member writes remain outside this slice;
union-containing struct copies preserve the overlapping member views. Compiler-dependent layout rules are tracked in
`issues/multiple-compilers.md`. Fixed multidimensional arrays of embedded
structs are supported through indexed leaf-field access and retain their
row-major shape in C0 metadata. Local arrays of those structs also accept
`[literal] = {...}` element designators, including nested designators for
multidimensional arrays; omitted elements remain zero-filled.

Named tagged unions are supported as embedded, read-only aggregates:

<!-- verified-example: mdtests/struct_tagged_union.md -->
```c
union packet_payload {
    int32 number;
    int32* pointer;
};

struct packet {
    int32 tag;
    union packet_payload payload;
};

int32 read_number(struct packet* packet) {
    if (packet->tag != 1) {
        return 0;
    }
    return packet->payload.number;
}
```

Union members all begin at byte offset zero. The union size and alignment are
the maximum of its modeled members, using the same LP64 ABI as structs. A
member expression is a typed load from the containing union's address, so the
member's pointer or scalar type is retained without inventing a runtime union
value. Taking the address of a scalar or pointer member preserves that same
containing allocation and produces the member's typed pointer (`int32*` for an
`int32` member, or `int32**` for an `int32*` member), so the resulting pointer
can be used for a read without materializing a whole-union value. The tag check
remains an ordinary C branch or Click precondition; the
current slice does not infer a mapping between arbitrary tag values and member
names. Union member writes, whole-union expressions, union locals or
parameters, arrays inside unions, and structs containing unions used by value
are rejected with explicit diagnostics. Direct member writes remain outside the
read-only slice.

Same-type struct fields may be declared in a comma-separated list, such as
`int32 first, second;`. Each field receives the same ABI layout it would have
received as a separate declaration, in source order.

Click contracts can use field places in resource clauses, such as
`views owner->len`, `owns owner->data`, and `owns packet->buf`. These lower
through the same ABI field offsets, preserve the array's element width, and
make the field loadable for symbolic execution. Explicit ranges such as
`owns owner[0..3]` are still available when a contract needs to describe a
broader footprint. Field places also work in `loadable(p->field)`, including
nested leaf fields such as `loadable(p->inner.value)`, and `owns p->field`
describes a field-sized footprint. The owned-resource verbs and `views` may name
an embedded aggregate directly, such as `owns p->inner` or `views p->items`.
Click expands that clause into one typed resource per scalar or inline-array
leaf, retaining each leaf's ABI offset, width, and metadata; a mixed-width
aggregate is never approximated as one int32 range.

## Heap allocation

C0 recognizes a deliberately small set of allocation patterns:

<!-- verified-example: mdtests/heap_free_owned_allocation_effect.md -->
```c
struct item *item = malloc(sizeof(struct item));
if (item == 0) {
    return 0;
}
item->value = 1;
free(item);
```

The assignment target supplies the pointee type. For struct pointers, the size
must be exactly
`sizeof(struct T)` for that same complete, imported struct, using the same LP64
layout calculation as field access and Click's `object(item)` resource. The
assignment form `item = malloc(sizeof(struct item));` is supported too.

`malloc` returns either null or a fresh base pointer. A normal null check must
refine that outcome before the function returns. Successful storage is
uninitialized: every field must be stored before it is read. `free(NULL)` is a
no-op; nonnull `free` requires the allocation base, complete owned access, and
the matching Click allocation authority.

For an `int32*`, C0 also accepts a runtime byte expression such as
`malloc(count * sizeof(int32))` (equivalently `malloc(count * 4)`). Verification
must prove that the resulting byte count is
positive, is an exact number of `int32` elements, and does not overflow signed
`int32`. Click can package the result as
`allocation(data, count * 4)` plus `data[0..count]`; `free(data)` consumes that
same symbolic extent. Direct deallocation is a certified heap-lifetime effect
authorized by those resources; it does not need a separate footprint clause or
to be routed through a helper function.

`calloc(count, sizeof(int32))` uses the same runtime extent and allocation
authority, but successful cells read as zero until a later store overwrites
them. A matching struct-pointer target may instead use
`calloc(count, sizeof(struct T))`; its supported scalar and pointer fields
read as zero or null until overwritten. Both forms require a positive,
non-overflowing element count, and the struct size must match the target
pointee type.

For a `uint8*`, C0 accepts byte-oriented forms such as
`malloc(count * sizeof(uint8))` and `calloc(count, sizeof(uint8))`. The
allocation extent is a positive `int32` byte count, and `data[i]` uses a
one-byte logical range element. Successful `malloc` storage is uninitialized;
successful `calloc` storage reads as zero. `free(data)` consumes the complete
one-byte range just as it does for the supported int32 and struct allocations.

For an `int32**` or `uint8**`, C0 accepts `malloc(count * sizeof(int32*))` or
`malloc(count * sizeof(uint8*))`. The allocation uses the LP64 eight-byte
pointer stride, so `slots[i]` addresses one pointer-valued cell and `free(slots)`
consumes the complete pointer-array range. Successful `malloc` storage is
uninitialized; each pointer cell must be stored before it is loaded. `calloc`
also accepts the matching `sizeof(int32*)` or `sizeof(uint8*)` form and makes
each successful pointer cell read as null until overwritten. A null cell may
be loaded and compared, but dereferencing it is still invalid.

For a live, nonzero pointer-array allocation, `realloc(slots, bytes)` accepts a
positive byte count that is an exact multiple of the matching eight-byte
pointer cell size. It preserves initialized pointer cells that fit in the new
extent and transfers the complete allocation authority to the successful
fresh result. When the source is a pointer-array `calloc`, the retained prefix
remains initialized to null and any grown tail is uninitialized.

For a live, nonzero `int32*` or `uint8*` allocation, `realloc(data, bytes)`
accepts a positive byte count. An `int32*` size must be an exact number of
`int32` elements; a `uint8*` size is already an exact number of byte elements.
It returns a pending null-or-success result like `malloc`: failure leaves
`data` and its allocation authority unchanged, while success retires the old
allocation, returns a fresh allocation, and preserves initialized cells whose
complete elements fit in the new extent. When the source is a bounded zeroed
`calloc` allocation, the preserved prefix remains zeroed and any grown tail is
uninitialized. Reallocations with other or unknown byte layouts remain
unsupported.

This is a modeled C0 builtin, not general libc compatibility. Zero-size
allocation, incomplete types, allocator results declared as `void *`,
unmodeled allocator prototypes, and non-concrete zeroed-prefix `realloc` cases
remain unsupported.
Heap byte extents still use Click's checked 32-bit memory-block extent; a
64-bit `size_t` extent is accepted when it is concrete or reduced by exact
contract facts to a value that fits that extent.

## Loops

`while` loops can be handled in two ways:

- bounded execution for small concrete loops
- loop verification conditions using a frontier-local
  `loop { invariant ... }` proof tactic

The first `for` slice is sugar for existing `while` semantics:
`for (i = init; condition; step) { body }` lowers to `i = init; while
(condition) { body; step; }`. The initializer may be a scalar assignment or a
scalar declaration initializer such as `int32 i = 0`, or it may be omitted.
The step may be a scalar assignment or one of the supported scalar
update-statement forms, or it may be omitted. The condition remains required
because unconditional loops need the separate `break` control-flow form. As in
C, `continue` executes the step before the next condition check. The step may
contain a comma-separated
sequence such as `i++, j--`; it is lowered in source order. Scalar assignment
initializers such as `i = 0, j = 1` and same-type declaration initializers
such as `int32 i = 0, j = 1` are lowered in the same way. Every declaration
declarator requires its own initializer.
As in C, an `if`, `else`,
`while`, or `for` may instead control one statement without braces; a local
declaration in that position is rejected because declarations require a
compound statement. An `else if` is parsed as an `else` arm containing another
`if`.

Symbolic pointer-writing loops should use invariants and explicit loop effects.
Do not expect unconstrained symbolic loops to be unrolled automatically.

## Unsupported or easy-to-forget C

These are not general C features yet:

- full structs, union forms outside the named embedded read-only slice, and enum forms outside the named scalar-field slice
- integer widths and signedness combinations outside the modeled scalar types
- casts beyond the current checked scalar conversions;
  the contextual null-pointer conversion for integer constant `0` is supported
- fully general symbolic narrowing between unlike 64-bit and narrower integer
  types
- pointer comparisons beyond the supported equality/range patterns
- general heap allocation beyond exact struct objects, runtime-sized `int32`
  arrays, and the supported `uint8` byte-buffer forms; arbitrary byte-layout
  reallocations remain unsupported
- `void` objects, named `void` parameters (a sole `(void)` denotes no parameters),
  `void **`, and untyped pointer
  dereference, indexing, or arithmetic
- extended-precision floating-point types (`long double`)
- variadic parameter lists (`...`)
- volatile forms outside the sequential scalar model described above
- const-qualified automatic/local aggregate objects, and broader qualifier
  conversions beyond scalar globals, scalar tables, const static-storage
  aggregates, pointer-to-const views, and one-level pointee-const casts
- designated initializers for inline scalar arrays and multidimensional scalar
  arrays, unresolved incomplete tentative arrays, other linkage forms, and
  wider string-literal forms;
  supported local and static-storage designated scalar-field aggregates,
  zero-initialized and positional compile-time-initialized scalar-field
  aggregates, scalar function-local and
  file-scope `static` objects, fixed or inferred scalar arrays,
  fixed or inferred one-dimensional arrays of scalar-field aggregates,
  multidimensional file-scope and function-local static scalar arrays,
  file-scope globals with compatible `extern` declarations, and basic ASCII
  read-only string literals are documented above
- `switch` case labels currently require integer or character literals, labels
  must be direct children of the switch compound body, and duplicate labels are
  rejected; arbitrary constant expressions, nested labels, and `goto` remain
  unsupported
- calls in `while`, `for`, and `do ... while` conditions are lowered into
  iteration guards that preserve reevaluation and `continue`; calls in
  conditional-expression branches are lowered through a lazy statement-level
  `if`; multiple calls in one unsequenced expression are rejected rather than
  choosing a C evaluation order
- update expressions inside larger expressions, such as `j = i++`
- compound/update operations on non-scalar lvalues, such as `p[i]++`
- initializers for arrays of structs or other unsupported aggregate objects
  outside the automatic/local and static-storage forms documented above
