# Supported C0

C0 is this repository's small C subset. It is not a standard language. The
subset exists so proof features can be developed against a precise target before
Click grows toward real C. When C0 syntax appears inside Surface Click, this
documentation calls that syntax a **C fragment**.

## Supported types

- `int32`
- `uint8`
- Standard spellings for the modeled integer types: under the supported LP64
  ABI, `int` and `int32_t` map to `int32`; `unsigned char` and `uint8_t` map
  to the one-byte `uint8`.
- `void` as a function return type
- `int32*`
- `uint8*`
- `int32**` and `uint8**`
- Function parameters written as `int32 p[]`, `int32 p[3]`, `uint8 p[]`, or
  `uint8 p[3]`, plus pointer arrays such as `int32* p[]`, lowered like C
  array parameters to pointers.
- Local fixed-size scalar arrays such as `int32 a[3];`, `int32 matrix[3][4];`,
  and `uint8 bytes[16];`.

Pointers are semantic objects with provenance blocks and pointer-offset terms.
They are not modeled as `int32` values. The current target layout assumes
8-byte pointer objects.

C0 accepts top-level aliases for the modeled scalar and named struct-pointer
types, such as `typedef int32_t index_t;` and `typedef struct item item_t;`.
The latter may be used as `item_t*`; struct values are still unsupported. The
accepted standard spellings are aliases into the existing C0 type model, not a
general C integer-conversion system. Plain `char` is rejected because the
current model does not represent signed `char`; use `unsigned char` or
`uint8_t` when a byte is intended.

The integer constant `0` is the supported null pointer constant. C0 converts
it to the canonical null pointer when returning or initializing a pointer,
assigning a pointer local or field, passing a pointer argument, and comparing
a pointer with zero. Nonzero integers do not implicitly convert to pointers;
this is not a general integer-to-pointer conversion or cast facility.

## Supported expressions and statements

Supported C0 surface includes:

- ordinary `//` line comments and `/* ... */` block comments
- integer literals and variables
- negative integer literals and unary `-`; negating `INT_MIN` remains signed
  overflow, while the literal `-2147483648` is representable
- ASCII byte character literals such as `'x'`, `'\n'`, and `'\0'`
- signed `+`, `-`, `*`, `/`, and `%`
- `int32` shifts `<<` and `>>`
- `int32` bitwise `&`, `|`, `^`, and unary `~` with fixed 32-bit
  two's-complement bitvector semantics
- signed comparisons and equality, with C's precedence: `==` and `!=` bind
  more loosely than `<`, `<=`, `>`, and `>=`, so `a == b < c` is
  `a == (b < c)`
- C logical `&&`, `||`, and unary `!` with short-circuit C scalar truthiness
- assignment, sequencing, empty blocks, and empty `;` statements
- scalar declaration initializers such as `int32 i = 0;`, and scalar array
  initializers such as `int32 values[3] = {1, 2, 3};` or nested
  `int32 matrix[2][3] = {{1, 2, 3}, {4, 5, 6}};`
- statement update sugar: `x++`, `x--`, `x += expr`, `x -= expr`, and
  `x *= expr`, and `x ^= expr`
- `if` with an optional `else`, using C scalar truthiness
- `while`
- assignment-style `for (init; condition; step)` loops lowered to `while`
- `return`
- bare `return;` and ordinary fallthrough from `void` functions
- address-of lvalues
- pointer arithmetic for `int32*` and `uint8*`, scaled by the pointee width
- pointer arithmetic for `int32**` and `uint8**`, scaled by their 8-byte
  pointer pointees
- pointer loads and stores, including pointer-valued cells through `T**`
- `p[i]` indexing for `int32*` and `uint8*`
- pointer-array indexing such as `p[i]` for `int32**` and `uint8**`
- row-major indexing for multidimensional scalar local arrays
- a small struct slice: `struct name { ... };`, `struct name*` pointers, and
  chained `p->child->field` loads/stores for `int32`, `uint8`, and pointer
  fields
- local arrays of the supported struct shapes, with indexed `items[i].field`
  loads and stores using the struct's LP64 stride
- known function calls through the current function environment, either
  assigned or used as standalone statements when the result is discarded
- `sizeof` for supported scalar and pointer types, and
  `malloc(sizeof(struct T))` assigned to a matching `struct T*`, runtime-sized
  `int32` backing allocation such as `malloc(count * sizeof(int32))`, zeroed
  runtime-sized `int32` allocation such as `calloc(count, sizeof(int32))`,
  matching zeroed struct allocation such as `calloc(count, sizeof(struct T))`,
  and standalone `free(pointer);`
- local scalar, pointer, and fixed-size array declarations for `int32`,
  `uint8`, and the supported struct shapes

Comparisons return C-style `int32` values: `0` or `1`. They are not Click
propositions by themselves. `uint8` rvalues promote to `int32` for arithmetic,
ordered comparisons, shifts, and bitwise operators. Assigning or returning an
`int32` into `uint8` requires Click to prove `0 <= value <= 255`.

C0 follows the GCC/Clang/MSVC consensus for signed right shift: `int32 >> k`
is arithmetic right shift with sign extension. This is implementation-defined
in ISO C for negative signed values, but it is the behavior of the mainstream
compilers Click is targeting.

## Undefined behavior

Signed overflow is C undefined behavior. Signed division and remainder also
have C undefined behavior for a zero divisor, and for `INT_MIN / -1` or
`INT_MIN % -1`. Shift counts must be in `0..32`. Signed left shift is undefined
for a negative left operand or an unrepresentable `int32` result. Proofs
involving signed arithmetic usually need requirements such as:

<!-- verified-example: mdtests/increment_requires_no_overflow.md -->
```click
requires x < 2147483647;
requires x > -2147483648;
```

Out-of-bounds memory accesses become proof obligations or undefined behavior
depending on the symbolic execution path. Prove access safety with viewed or
owned memory resources, `loadable(...)`, index bounds, and loop invariants.

Automatic scalar, pointer, and array declarations do not zero-initialize their
storage. Reading a local before a value has been written is undefined behavior.
Declaration initializers such as `int32 i = 0;` are lowered as a declaration
followed by the initializing assignment.

Scalar parameters are callee-owned objects, just like scalar locals. If a
parameter's address is taken, Click gives that parameter a distinct stack slot
for the current call, and stores through the address are visible to later reads
of the parameter by name. The slot is separate from any caller variable with
the same spelling and from slots in recursive calls. Pointer-to-pointer
parameters use 8-byte pointer cells and can be indexed and dereferenced like
ordinary C pointer arrays.

## Local arrays

Local arrays allocate stack memory blocks:

<!-- verified-example: mdtests/uint8_local_array.md -->
```c
uint8 local_byte_array() {
    uint8 a[2];
    a[0] = 'x';
    a[1] = 'y';
    return a[0];
}
```

An array name decays to a pointer rvalue for indexing and function arguments.
Direct assignment to an array object is rejected. `int32` arrays allocate four
bytes per element; `uint8` arrays allocate one byte per element. A local array
initializer writes each element in declaration order; omitted elements are
zero-initialized, and too many elements are rejected.

Scalar local arrays may have multiple fixed dimensions, such as
`int32 matrix[3][4]`. C0 flattens these arrays in row-major order while
retaining the declared element width, so `matrix[i][j]` carries the same
bounds and pointer-arithmetic obligations as an equivalent flat access.

## Struct subset

C0 supports a small struct-pointer slice:

<!-- verified-example: mdtests/struct_multifield_explicit_permissions.md -->
```c
struct owner {
    int32 len;
    int32* data;
};

int32 set_first(struct owner* owner, int32 data[]) {
    int32* current;
    owner->len = 1;
    owner->data = data;
    current = owner->data;
    current[0] = owner->len;
    return current[0];
}
```

This is intentionally not a full C struct model yet. Struct fields may be
`int32`, `uint8`, or pointer-typed fields such as `int32*`, `uint8*`, and
`struct name*`. The standard spellings for `int32` and `uint8` are accepted in
the same positions. `struct name*` is accepted for parameters, local pointers,
and fields. The importer retains the pointee struct name across intermediate
field loads, so `p->child->field` remains typed. Fields use the documented LP64
ABI: each field is aligned, pointers occupy eight bytes, and the struct size
includes tail padding. Struct values, embedded struct values, arrays of
structs, unions, bitfields, packed layout, and general field-address expressions
are still unsupported.

Click contracts can use field places in resource clauses, such as
`views owner->len` and `owns owner->data`. These lower through the same
ABI field offsets, and the access resource makes the field loadable for
symbolic execution. Explicit ranges such as `owns owner[0..3]` are still
available when a contract needs to describe a broader footprint. Field places
also work in `loadable(p->field)`, and `mutable p->field` describes a
field-sized effect.

## Heap allocation

C0 recognizes one deliberately small allocation pattern:

<!-- verified-example: mdtests/heap_free_owned_allocation_effect.md -->
```c
struct item *item = malloc(sizeof(struct item));
if (item == 0) {
    return 0;
}
item->value = 1;
free(item);
```

The assignment target supplies the pointee type. For struct pointers, the size
must be exactly
`sizeof(struct T)` for that same complete, imported struct, using the same LP64
layout calculation as field access and Click's `object(item)` resource. The
assignment form `item = malloc(sizeof(struct item));` is supported too.

`malloc` returns either null or a fresh base pointer. A normal null check must
refine that outcome before the function returns. Successful storage is
uninitialized: every field must be stored before it is read. `free(NULL)` is a
no-op; nonnull `free` requires the allocation base, complete owned access, and
the matching Click allocation authority.

For an `int32*`, C0 also accepts a runtime byte expression such as
`malloc(count * sizeof(int32))` (equivalently `malloc(count * 4)`). Verification
must prove that the resulting byte count is
positive, is an exact number of `int32` elements, and does not overflow signed
`int32`. Click can package the result as
`allocation(data, count * 4)` plus `data[0..count]`; `free(data)` consumes that
same symbolic extent. Direct deallocation is a certified heap-lifetime effect
authorized by those resources; it does not need to appear in a `mutable`
segment or be routed through a helper function.

`calloc(count, sizeof(int32))` uses the same runtime extent and allocation
authority, but successful cells read as zero until a later store overwrites
them. A matching struct-pointer target may instead use
`calloc(count, sizeof(struct T))`; its supported scalar and pointer fields
read as zero or null until overwritten. Both forms require a positive,
non-overflowing element count, and the struct size must match the target
pointee type.

This is a modeled C0 builtin, not general libc compatibility. Zero-size
allocation, arbitrary byte layouts, incomplete types, `size_t`, `void *`
conversions, allocator prototypes, casts, and `realloc` remain
unsupported.

## Loops

`while` loops can be handled in two ways:

- bounded execution for small concrete loops
- loop verification conditions using a frontier-local
  `loop { invariant ... }` proof tactic

The first `for` slice is sugar for existing `while` semantics:
`for (i = init; condition; step) { body }` lowers to `i = init; while
(condition) { body; step; }`. The initializer may be a scalar assignment or a
scalar declaration initializer such as `int32 i = 0`. The step may be a scalar
assignment or one of the supported scalar update-statement forms. Omitted
clauses and `continue` are not supported yet.

Symbolic pointer-writing loops should use invariants and explicit loop effects.
Do not expect unconstrained symbolic loops to be unrolled automatically.

## Unsupported or easy-to-forget C

These are not general C features yet:

- full structs, unions, enums
- unsigned integers other than the narrow `uint8` byte type
- integer widths other than `int32`
- casts beyond the current checked `int32`-to-`uint8` narrowing conversion;
  the contextual null-pointer conversion for integer constant `0` is supported
- mixed-width integer conversions beyond `uint8` promotion to `int32`
- pointer comparisons beyond the supported equality/range patterns
- general heap allocation beyond exact struct objects, runtime-sized `int32`
  arrays, and the supported zeroed `int32` form
- `void` objects, `void` parameters, and `void *`
- function pointers
- floating-point types (`float` and `double`)
- variadic parameter lists (`...`)
- the `volatile` qualifier
- global variables
- `do while`, `switch`, `break`, `continue`
- a block-scoped declaration that shadows a parameter or an enclosing local
  (sibling blocks may reuse a name; Click rejects the shadowing form rather
  than modeling it)
- omitted clauses inside `for` loops
- update expressions inside larger expressions, such as `j = i++`
- compound/update operations on non-scalar lvalues, such as `p[i]++`
- array initializers for structs and other aggregates

If you need one of these, add the smallest mdtest that motivates it before
expanding the parser or kernel.
